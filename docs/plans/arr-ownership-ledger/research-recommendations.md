## Executive Summary

YAN-516 / #351 can ship in **one PR** if scoped to **customFormat + qualityProfile only** (the `qualityProfiles` section). Other sections need no ledger rows in this PR: `delayProfile`, `naming`, `mediaSettings`, `qualityDefinitions` are singletons/bulk-writes with no "removed upstream" semantics, and `metadataProfile` (Lidarr) is a named entity but is out of the acceptance criteria. The ledger schema stays general (`section`, `entity_type`) so metadata profiles can be added later; the writer uses an **allowlist** so singleton outcomes never create rows.

Findings that shape the design (all paths relative to `packages/praxrr-app/src/lib/server/`):

1. **The preview already emits `delete` for every unmatched Arr entity, hand-made ones included.** `diffEntityCollection` (`sync/preview/sectionDiffs.ts:211-225`) adds a `delete` EntityChange for every current Arr entity not consumed by a desired one. Drift maps `delete` to category `unmanaged` (`sync/drift/check.ts:146-150`) and excludes it from the signature (`check.ts:263-270`, `drift/persist.ts:59`). Pruning MUST NOT be derived from these changes. Prune candidates come from `ledger ∩ not-desired ∩ live-Arr-id+name-match`, and the preview needs an explicit managed-vs-unmanaged marker on delete changes. This is the main way criterion 2 fails if done carelessly.
2. **"Expected set" logic exists only inside `scanForStaleItems`** (`sync/cleanup.ts:57-230`). It already encodes the fail-closed rules: PCD cache unavailable keeps the namespace (`:80-90`), TRaSH `no_cache`/`transform_failed` keeps all TRaSH suffixes (`:117-130`), a TRaSH source with no assigned namespace keeps everything (`:136-143`), and missing TRaSH profiles keep their namespace (`:147-160`). Prune planning must reuse this logic, not re-derive it. Extract it into a shared resolver that the cleanup scan and the prune planner both call.
3. **Every Praxrr-written CF/QP name carries an invisible namespace suffix**, indexed per (instance, database) or (instance, TRaSH source) (`sync/namespace.ts:11-45`; `arrTrashNamespaces.ts` rows are never reused). So a hand-made CF essentially never matches a suffixed name. That makes "update outcome by suffixed-name match" strong ownership evidence, which drives the backfill recommendation.
4. **Reviewed apply is the only path that can safely delete.** `executeReviewedSyncJob` (`jobs/handlers/arrSync.ts:505-783`) re-materializes the preview, compares evidence, and runs syncers from frozen `PreparedExecutionContext`s with current-value guards (QP guards at `qualityProfiles/syncer.ts:696-731`). Ordinary/scheduled syncs (`arrSyncHandler`, `arrSync.ts:785`) have no review and MUST never delete. This satisfies "always preview first" structurally rather than by convention.
5. **Outcomes lack provenance.** `SyncEntityOutcome` (`sync/types.ts:46-61`) has `name` (unsuffixed PCD name) and `remoteId`, but no `sourceKind`, `databaseId`, or suffixed Arr name. These exist in the QP batch (`DatabaseSyncBatch.sourceKind/databaseId/suffix`, `qualityProfiles/syncer.ts:83,141,178,940,1095`). For TRaSH batches `databaseId = -source.id` (`syncer.ts:1098`). Do not persist the negative-id trick; store `database_id` = positive source id plus `source_kind='trash'`.
6. **Existing infrastructure carries most of acceptance criterion 3 for free.** `SyncEntityAction` already includes `'delete'` (`types.ts:19`); `sync_history.entity_outcomes` is an opaque JSON blob (`migrations/20260720_add_sync_history_entity_outcomes.ts`); `SyncPreviewAction` includes `'delete'` (`preview/types.ts:10`); history `changes` come from `flattenSyncPreviewChanges` (`syncHistory/record.ts:87-123`). Drift and Canary need explicit semantics work (see Phase 4).

Recommended backfill: **adopt on next confirmed write** (create or update success of a suffixed-name entity), with no name-based speculative adoption and no startup scan. Legacy orphans stay reachable only through cleanup's explicit "include unmanaged" mode. Details below.

### Recommended Implementation Strategy

Scope: one PR, five commits/phases, ordered so each phase is independently testable and the destructive path lands last behind a default-off policy.

#### Phase 0: Shared expected-set resolver (pure refactor, no behavior change)

- Extract steps 1-1b of `scanForStaleItems` (`cleanup.ts:62-187`) into `sync/expectedConfig.ts` returning `{ expectedQPNames, expectedCFNames, keepSuffixes, keepAllTrashSuffixed, inKeptNamespace(name) }`. Keep the log messages byte-identical (TRaSH resolver already promises this, `trashSourceProfiles.ts:30`).
- `cleanup.ts` keeps its public API; the existing cleanup tests (`tests/` aliases `cleanup`) must still pass unchanged.
- Reason: `cleanup.ts` is 358 lines and `qualityProfiles/syncer.ts` is 1458 (already over the ~500 soft cap), so all new logic goes in new modules, not in the syncer.

#### Phase 1: Ledger table + query module + policy column (additive migration)

- Migration (next version after `20261024_bound_schedule_intervals.ts`; use `_template.ts`): `arr_managed_entities`
  - `id INTEGER PK`, `instance_id` FK `arr_instances(id) ON DELETE CASCADE` (pattern from `20261023_create_arr_trash_guide_namespaces.ts`), `arr_type TEXT CHECK IN ('radarr','sonarr','lidarr')` (explicit per-type, no sibling fallback), `section`, `entity_type CHECK IN ('customFormat','qualityProfile')`, `remote_id INTEGER`, `arr_name TEXT` (**suffixed live name**, added beyond the issue spec for the delete-time guard), `pcd_name TEXT` (unsuffixed), `source_kind CHECK IN ('pcd','trash')`, `database_id INTEGER` (PCD database id, or TRaSH source id when `source_kind='trash'`), `first_synced_at`, `last_synced_at`.
  - `UNIQUE(instance_id, entity_type, remote_id)` and `UNIQUE(instance_id, entity_type, arr_name)`; upsert on `arr_name` conflict updates `remote_id` and `last_synced_at` but preserves `first_synced_at`.
- Policy: add `prune_removed_managed INTEGER NOT NULL DEFAULT 0` to `arr_instances`. Follow the `detected_version?` pattern (optional in the `ArrInstance` interface so hand-built test mocks do not break, `db/queries/arrInstances.ts:18-20`). Extend `collectArrInstanceUpdates` (`:90-135`), the settings form action (`routes/arr/[id]/settings/+page.server.ts:126-251`), and the `/api/v1` instance schema. A separate policy table is the alternative; the column is simpler and the cost is touching a few test mocks.
- Query module `db/queries/arrManagedEntities.ts`: `upsert`, `listByInstance(entityType?)`, `deleteByRemoteId`, `deleteByInstance`. App-DB-only, so `seedBuiltInBaseOps.ts` is intentionally untouched (same as `20260720`).
- Invalidate the ledger when the instance's identity changes. `arrInstancesQueries.update` clearing the ledger on `url`/`type`/credential changes prevents ids from one Arr being applied to another (see Risk Mitigations).

#### Phase 2: Ledger writes from confirmed outcomes (no deletes yet)

- Write rows **at the write site**, not only at history-record time, so a crash between the Arr write and `recordSyncHistory` cannot drop provenance. `writeCustomFormatPayload` (`customFormats/syncer.ts:66-132`) already knows `instanceId`/`instanceType` and returns the success outcome with `remoteId`; QP writes go through `writeQualityProfilePayload` (`qualityProfiles/syncer.ts:~1305`). Add an optional `ownership: { sourceKind, databaseId, arrName }` parameter, passed from the batch (`batch.sourceKind`, `batch.databaseId`, suffixed `payload.name`).
- Record only when `status==='success'` and `action` is `create` or `update` and `remoteId` is a positive integer. Skipped/failed outcomes never create or advance rows.
- Cover **both** execution paths: the ordinary `syncQualityProfiles`/CF path (`syncer.ts:381-392,407-419`) and the reviewed path (`syncPreparedQualityProfiles`, `:711-780`). A shared `recordManagedEntity()` in `sync/ledger/record.ts` is called from both.
- Ledger writes never throw into the sync (log and continue); a missing row only means "not pruneable", which is the safe direction.
- Optionally add the optional provenance fields to `SyncEntityOutcome` so history and UI can show "managed" without a join. This requires checking the OpenAPI outcome schema for `additionalProperties` (**uncertain, not verified**); if strict, keep provenance out of the outcome and compute it at read time from the ledger.

#### Phase 3: Prune planner + reviewed-only executor

- `sync/ledger/prunePlan.ts` (pure): inputs = ledger rows, resolved expected set (Phase 0), live Arr CFs/QPs (already fetched into `currentGuards`, `qualityProfiles/syncer.ts:614-617`). A ledger row is a prune candidate iff **all** hold:
  1. policy `prune_removed_managed = 1` and this is a reviewed-preview materialization;
  2. the row's `arr_type` equals the instance type;
  3. a live entity exists with the same `remote_id` **and** exact `name === arr_name` (id-reuse and renamed-by-hand guard);
  4. `arr_name` is not in the expected set **and** not in a kept namespace (`inKeptNamespace`); namespaces whose desired contents are undeterminable are skipped wholesale;
  5. for CFs: no desired profile still references it (union across all batches; the expected set is already a union).
- Put the plan into the frozen `QualityProfilesPreparedExecutionContext` as `desired.prune` (`{ customFormats: [{arrName, remoteId}], qualityProfiles: [...] }`). Because the review binding hashes materialized evidence, a changed ledger/policy/expected set between review and apply invalidates the review (`scope_drift`/evidence mismatch) rather than deleting something un-reviewed. Record the ledger snapshot via `recordPreviewEvidence` (`base.ts:135`); whether to reuse the `'pcd'` class (app-side desired state) or add a `'ledger'` class is open (a new class touches `SyncPreviewEvidenceClass`, `preview/types.ts:17`, and `changedEvidence` in the API contract). Default: reuse the `'pcd'` class with key `managedLedger` and avoid a contract change.
- Executor (new `sync/ledger/prune.ts`, **not** `cleanup.deleteStaleItems`, which maps any HTTP 500 to "assigned to media" and returns arrays rather than outcomes, `cleanup.ts:307-345`): runs after all create/update writes in `syncPreparedQualityProfiles`, **QPs first, then CFs** (profiles stop referencing a CF before it is removed; the opposite of cleanup's order; whether Arr cascades CF removal from profiles is **unverified** and ApiResearcher should confirm per `arr_type`). For each target:
  - re-check the frozen guard against live Arr id+name (pattern at `syncer.ts:696-731`); mismatch aborts that entity as `skipped` with a sanitized reason;
  - call `client.deleteQualityProfile`/`deleteCustomFormat` (`arr/base.ts:254-255,293-294`, per PracticesResearcher); errors through `sanitizeArrWriteError` (as in `customFormats/syncer.ts:107`);
  - emit `SyncEntityOutcome{ action:'delete', status, remoteId, reason }`: `success`, `skipped` (HTTP 500 on QP maps to "assigned to media", reason string reused from cleanup; already-absent 404), `failed` (other errors);
  - delete the ledger row only on confirmed `success` or confirmed-absent; keep it on `skipped`/`failed` so the next review retries.
- "Skip QPs that media is still assigned to": v1 relies on the Arr's refusal (HTTP 500, existing behavior) classified as `skipped`. A pre-check from library endpoints (`routes/api/v1/arr/library`) in the preview is more informative but heavier and Arr-type-specific; defer.
- Critical branch fix: the ordinary QP sync early-returns when no profiles are selected (`syncer.ts:373-378`), but the reviewed path must still plan prune when the user deselects the last profile. Ensure `generatePreview` and `syncPreparedQualityProfiles` handle an empty desired set with a non-empty prune plan, while distinguishing "user deselected" from "selection dropped because undeterminable" (skipped outcomes / `keepSuffixes` fail closed).
- Ordinary and scheduled syncs never receive a prune plan. They only count pending prune candidates for display.
- Preview/UI: split delete changes into "Will delete (Praxrr-managed)" and "Unmanaged (not touched)". This needs an additive `ownership` marker on delete `EntityChange`s (OpenAPI first, contract-first rule). The apply dialog should show the prune list explicitly; the apply route (`routes/api/v1/sync/preview/[previewId]/apply/+server.ts:244-306`) needs no new protocol since prune is part of the reviewed qualityProfiles section.

#### Phase 4: Surfacing delete outcomes in history, drift, Canary (criterion 3)

- **Sync history**: `entityOutcomes` already persists any `action`; `changes` already include deletes via `flattenSyncPreviewChanges`. Needed: UI labeling, filters on `action='delete'`, and `deriveSyncHistoryStatus` (`syncHistory/record.ts:45-64`) treating `failed` deletes like other failed outcomes (verify with a test).
- **Drift**: today `delete` means "unmanaged" and is invisible to the signature. Managed pending-prune items need distinct semantics: either a new `DriftCategory` such as `removed_upstream` for `delete`+`ownership:'managed'` (included in the signature only while the policy is on), or leave drift unchanged and expose a separate pending-prune count. Prefer the new category (criterion 3 asks for drift visibility), at the cost of an OpenAPI enum change plus a drift-summary migration check (`drift/summary.ts`, `drift/persist.ts:59`). Flag for TechDesigner.
- **Canary**: the coordinator classifies from the newest `sync_history` row (`canary/coordinator.ts:79-136`) and stores planned preview evidence (`remaining_preview_evidence`, migration `20260723_add_canary_preview_evidence.ts`, `canary/types.ts:60-98`). Prune plans appear in canary evidence if they are inside the preview payload; verify the evidence projection does not filter `delete` and that the blast-radius gate counts destructive actions. I did not trace the Canary evidence serializer in depth, so this is **[INFERENCE]** and needs a test.

#### Phase 5: Cleanup scoped to the ledger (default) with "include unmanaged"

- Add `scope: 'managed' | 'all'` to `scanForStaleItems` / `executeCleanup` (`cleanup.ts:57,244`) and to the request parser (`cleanupRequest.ts`, which currently parses `{action, instanceId, scanResult}` only) and `/api/v1/arr/cleanup` (OpenAPI first). Default `managed`: stale = ledger rows whose live entity matches id+name and which are not expected/kept. `all` preserves today's "anything unexpected" behavior.
- Keep YAN-471's invariant: execute re-scans server-side and deletes only requested items that are still stale and match id+name (`cleanup.ts:249-272`); the scope is passed in the request and re-applied on the re-scan, never trusted from client item lists.
- Remove ledger rows for entities deleted through cleanup (both scopes).
- UI (`routes/arr/components/CleanupModal.svelte`): show a count of "unmanaged items not in scope" with an opt-in toggle, because a fresh install of this feature has an empty ledger (see backfill) and `managed` scope will otherwise look like cleanup broke.

#### Suggested test matrix (map to acceptance criteria)

- AC1: CF removed from PCD, policy on, reviewed apply deletes exactly the ledger CF and writes a `delete` outcome; unreviewed/ordinary sync deletes nothing; evidence drift between review and apply invalidates.
- AC2: hand-made CF (no suffix, no ledger row) with the same human name never appears in the prune plan; ledger row whose live name was changed by hand is skipped; same-id/different-name skipped.
- AC3: history row contains the `delete` outcome and change; drift shows the managed category; Canary evidence includes the planned delete.
- Fail-closed: PCD cache missing, TRaSH `no_cache`/`transform_failed`/missing profile, empty ledger, ledger query throwing, policy off, wrong `arr_type`: no deletes.
- Per `arr_type` (radarr, sonarr, lidarr): ledger CHECK, delete endpoint dispatch, no sibling fallback. Test with exact `instance_id` targets, per the repo's rename-propagation rule.
- QP media-assigned: HTTP 500 gives `skipped`, ledger row retained.

### Backfill policy options and recommendation

| Option                              | Behavior                                                                                      | Pros                              | Cons                                                                                                                                                                                                                                                       |
| ----------------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Forward-only                     | Ledger rows only from creates/updates confirmed after the ledger ships                        | Strictest provenance, no guessing | Entities created pre-ship are unmanaged until their next write. Since each selected entity is updated on every full sync, rows populate on the first post-ship sync anyway. Entities already orphaned (removed from PCD before ship) are never auto-pruned |
| B. Adopt name-matched on next sync  | Treat any live entity whose name matches a desired suffixed name as Praxrr-owned at sync time | Same coverage as A in practice    | Differs from A only in concept: a name match with a _suffixed_ name is already what the syncer's update path does (`customFormats/syncer.ts:75-79` update by `payload.id` from name match)                                                                 |
| C. Startup/background scan adoption | Scan Arr and adopt all suffixed entities                                                      | Would catch legacy orphans        | Adopts entities Praxrr no longer expects, which is exactly what cleanup flagged stale; contradicts "never delete what we cannot prove we wrote"; another destructive-adjacent surface                                                                      |

**Recommendation: A, implemented as B's write path.** Record a ledger row on every confirmed `create` _or_ `update` success. An update is proof Praxrr wrote the entity this run, and because every Praxrr name carries the namespace suffix, an update of a suffixed-name match is overwhelmingly an entity Praxrr created in an earlier run (pre-ledger). Do **not** adopt anything Praxrr did not write in the current run: no startup scan, no adoption of entities that are merely present. Entities orphaned before the ledger shipped remain visible only through cleanup's explicit `include unmanaged` mode (the user confirms each item through the existing re-scan flow).

Consequences to document in the PR/docs: (1) after upgrade, the ledger is empty until a sync runs; pruning with an empty ledger deletes nothing (fail-closed); (2) the first post-ship sync populates rows for everything currently selected; (3) a user who removes a CF from the PCD _before_ any post-ship sync of that CF can still clean it via `include unmanaged`; (4) consider showing "ledger populated N/M" in instance settings next to the policy toggle, and warn when enabling the policy on an unpopulated ledger.

Edge: a hand-made CF that the user manually renamed to equal a desired suffixed name (they would need to type the zero-width suffix) would be adopted on update. That is accepted as the same risk the syncer already takes by overwriting it; the delete-time id+name guard and reviewed preview still bound the blast radius.

### TRaSH interplay (source_kind)

- `source_kind='trash'` rows come from TRaSH batches (`qualityProfiles/syncer.ts:1095`); `database_id` stores the positive TRaSH source id (never the `-source.id` batch trick at `:1098`). Namespace is the persisted per-(instance, source) index (`arrTrashNamespaces.ts`; `getTrashGuideNamespaceSuffix`, `namespace.ts:38-41`), so TRaSH and PCD suffixes cannot collide (`isTrashGuideNamespaceSuffix`, `:63`).
- "Removed upstream" for TRaSH means a CF is dropped from a selected, **resolved** profile (`resolution.portableProfilesByName` scores, `cleanup.ts:162-173`) and is no longer referenced by any selected profile of that source. That is prunable.
- Fail closed (copy cleanup's rules): do not plan pruning for a TRaSH source whose resolution status is `no_cache`/`transform_failed` (`cleanup.ts:117-130`), whose namespace is unassigned (`:136-143`), or whose selected profile is missing from the source (`:147-160`, which may be a transient upstream rename). Deleted or unavailable TRaSH sources: leave rows alone in v1 and show them under `include unmanaged`; add an explicit "remove source and prune" decision later.
- TRaSH CFs may be shared by name with PCD CFs but have different suffixes, so they get separate ledger rows (`UNIQUE(instance_id, entity_type, arr_name)` includes the suffix).
- Prune confirmation UI should show provenance (`source_kind`, source/database name) per item so users can tell TRaSH-driven removals from PCD-driven ones.

### Risk Mitigations

| Risk                                                                                                                                   | Impact                                                    | Mitigation                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prune derived from preview `delete` changes (which include hand-made entities)                                                         | Deletes unmanaged data; violates AC2                      | Prune plan built only from `ledger ∩ not-expected ∩ live id+name`. Add an `ownership` marker on delete EntityChanges; unit test that an unmanaged `delete` change never produces a prune target                                                                                              |
| Stale/mismatched ledger (Arr reinstalled, DB restored, id reuse, instance URL repointed to another Arr)                                | Wrong entity deleted                                      | Store `arr_name` and require live `id` and exact `name` match at plan time and again at execute time (frozen guards). Clear ledger rows on instance `url`/`type`/credential change. Never trust `remote_id` alone                                                                            |
| Undeterminable desired state (PCD cache unavailable, TRaSH cache/transform failure, partial selection fetch) read as "nothing desired" | Mass deletion                                             | Shared resolver with cleanup's `keepSuffixes`/`keepAllTrashSuffixed`; prune skips whole namespace; abort prune if any batch had skipped/failed outcomes; test each case                                                                                                                      |
| Prune running without review (scheduled/ordinary sync, drift check, history capture)                                                   | Silent destructive change                                 | Prune plan exists only inside the reviewed `PreparedExecutionContext`; `syncer.sync()` ordinary path has no delete code path. Preview-only callers (drift, history pre-capture) show candidates but cannot execute                                                                           |
| Review/apply race (policy toggled, ledger changed, PCD edited between preview and apply)                                               | Deleting un-reviewed items                                | Include policy value and ledger snapshot in the evidence hash; `executeReviewedSyncJob` already re-materializes and invalidates on mismatch (`arrSync.ts:578-609`); 10-min preview TTL (`preview/store.ts:19`)                                                                               |
| QP still assigned to media                                                                                                             | Arr refuses (HTTP 500) or, worse, behavior differs by Arr | Treat as `skipped` and keep row; sanitize the reason; verify DELETE semantics per `arr_type` (ApiResearcher); optional preview-time in-use check deferred                                                                                                                                    |
| CF deleted while a surviving QP references it                                                                                          | Arr 4xx or implicit profile mutation                      | Delete QPs before CFs; surviving profiles are updated first so they no longer score the CF; confirm Arr cascade behavior per `arr_type`                                                                                                                                                      |
| Ledger write failure or crash between Arr write and history                                                                            | Lost provenance                                           | Write at the write site (before the history row), upsert idempotently; a missing row = not pruneable (safe direction); next sync's update re-adopts it                                                                                                                                       |
| Default cleanup scope change surprises existing users (empty ledger, scan finds nothing)                                               | Perceived regression of YAN-444/471 flows                 | UI shows unmanaged count and an explicit "include unmanaged" toggle; document in changelog/docs; keep `all` scope byte-compatible with current semantics                                                                                                                                     |
| Contract drift (OpenAPI vs validators vs handlers)                                                                                     | Repo policy violation                                     | Contract-first: update `packages/praxrr-api/openapi.json`, `deno task generate:api-types`, add policy field, cleanup `scope`, delete-change `ownership`, drift category; keep validators in lockstep                                                                                         |
| File size/cohesion (`qualityProfiles/syncer.ts` 1458 lines, `arrSync.ts` 1206 lines)                                                   | Maintainability                                           | New code in `sync/ledger/*` and `sync/expectedConfig.ts`, thin call sites only                                                                                                                                                                                                               |
| Cross-Arr assumptions                                                                                                                  | Wrong semantics per app                                   | `arr_type` column with CHECK, explicit dispatch by `arr_type`, fail fast on unknown type; Lidarr entities treated per its own tables (no Sonarr fallback); verify CF/QP delete endpoints per app before enabling policy for that type, and block the policy toggle for any type not verified |
| `Last-selection deselected` path skipped by early return                                                                               | Removed profile never pruned                              | Handle empty-desired + non-empty-prune in preview and reviewed executor (`syncer.ts:373-378`) with an explicit "user deselected" vs "undeterminable" distinction                                                                                                                             |
| Delete outcome + ledger row deletion not atomic                                                                                        | Orphan ledger row or lost row                             | Delete ledger row after confirmed Arr delete; a leftover row for an absent entity is harmless (id+name guard fails, row reconciled on next scan/sync); log reconciliation                                                                                                                    |

### Deferrable follow-ups (explicitly out of this PR)

- Ledger rows and prune for `metadataProfile` (Lidarr) and any future named entities.
- Preview-time "media assigned" detection via library endpoints per Arr type.
- Automatic (scheduled) pruning with an approval gate or per-run delete cap (blast-radius limit).
- Ledger reconciliation job (drop rows whose live entity vanished), and a "managed entities" inspector UI/API (`GET /api/v1/arr/{id}/managed-entities`).
- Handling deleted/unavailable TRaSH sources ("remove source and prune").
- Adoption UI for pre-ledger orphans (explicit per-item "adopt" instead of `include unmanaged` delete).
- Notifications on prune outcomes; Canary per-cohort prune caps.
- Removing `CleanupModal`'s legacy copy once `managed` scope is the norm.
