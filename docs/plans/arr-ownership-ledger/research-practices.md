## Executive Summary

Praxrr already has the necessary Arr DELETE transports, confirmed per-write outcome contract, reviewed-preview evidence lifecycle, server-side cleanup re-scan, and isolated SQLite/fake-client test patterns. Reuse these rather than introducing a second sync or job framework. The missing pieces are a durable ownership query module, explicit source provenance at the write boundary, a managed-only prune planner, and a reviewed delete writer; the present cleanup classification and deletion helper are **not** safe drop-in implementations of automatic pruning. Keep new logic in small cohesive modules instead of extending the already 1,458-line quality-profile syncer, and treat absence of source data as unknown—not as an empty desired set.

Paths below are repository-relative to this worktree; app paths start at `packages/praxrr-app/src/`. Research only: no code, tests, builds, or migrations were executed.

### Cleanup scan and execution

- Reuse the desired-name/source-resolution work in `packages/praxrr-app/src/lib/server/sync/cleanup.ts:62-174`: PCD selections, namespace lookup, referenced CF names, TRaSH source hydration, and explicit target `arrType`. The important conservative behavior is already implemented: missing PCD cache protects its namespace (`:79-89`); unavailable TRaSH source protects TRaSH namespaces (`:117-129`); unassigned persisted namespace and missing selected profile protect affected entities (`:134-160`). Preserve these guards when extracting desired-set logic.
- **Do not reuse “all unexpected remote items are stale” as authorization.** Current loops classify every nonexpected QP/CF as stale (`cleanup.ts:192-213`), including hand-made entities. Replace the default candidate universe with ledger IDs; explicit include-unmanaged mode must remain separate from automatic pruning. Namespace suffixes are presentation/source-isolation aids, not ownership proof.
- Reuse `executeCleanup`'s fresh server-side scan and intersection (`cleanup.ts:238-272`): exact **ID and name** matching, one execution per ID, and server-owned returned items. The rejected-item reporting is at `:289-299`. Extend this flow so scan and execute share the same explicitly validated scope/mode; a stale client payload must not enable unmanaged deletion.
- `deleteStaleItems` (`cleanup.ts:302-358`) offers useful sequential deletion/accounting structure but returns cleanup-specific arrays rather than confirmed sync outcomes. It also surfaces raw exception messages (`:321-326,337-343`) and assumes any QP HTTP 500 is assignment. Reuse transport and accounting ideas, not this function unchanged as the pruning engine. Its CF-first ordering (`:303,316-334`) must not be adopted as proof of safe dependency ordering for every Arr.
- Boundary validation belongs in the existing `packages/praxrr-app/src/lib/server/sync/cleanupRequest.ts`: discriminated scan/execute request (`:8-11`), positive IDs and bounded arrays (`:13-30`), then decoded-body validation (`:35-65`). Add the contract-defined mode here rather than spreading body parsing through route and sync code; preserve the 10,000-item bound.

### Confirmed outcomes, provenance, and reviewed execution

- Keep the canonical `SyncEntityOutcome` (`packages/praxrr-app/src/lib/server/sync/types.ts:46-61`). Its action union already includes `delete` (`:14-19`), and `SyncResult.outcomes` is required (`:70-80`). Success must come from a resolved Arr write, never from an `EntityChange` or preview count (`:40-44`).
- `writeCustomFormatPayload` is the reusable confirmed-write pattern (`packages/praxrr-app/src/lib/server/sync/customFormats/syncer.ts:58-132`): require a positive create response ID; return exactly one success/failed outcome with explicit target `arrType`; sanitize failures. Both normal and reviewed CF execution can use it. It is not currently a generic action/outcome builder.
- QP equivalent is private `writeQualityProfilePayload` (`packages/praxrr-app/src/lib/server/sync/qualityProfiles/syncer.ts:1317-1407`); ordinary execution consumes it at `:1300-1310`. Prefer a narrowly extracted shared QP writer if the new feature needs this seam, rather than duplicating outcome constructors or adding broad callbacks to `BaseSyncer`.
- **Source context must be retained before flattening outcomes.** Outcomes contain unsuffixed name, section, Arr type, remote ID, action/status, and reason—but no `databaseId` or `sourceKind` (`types.ts:46-61`). `DatabaseSyncBatch` and prepared batches already carry both (`qualityProfiles/syncer.ts:82-89,140-146`). Record/enrich ownership at a boundary where that batch context is still authoritative. Never infer database identity from outcome name, remote suffix length, or order in the final outcome array.
- A successful **update** proves Praxrr wrote an existing object, not that Praxrr created it. Current CF matching adopts an existing exact suffixed name (`customFormats/syncer.ts:191-194`); QP matching similarly uses an existing name map (`qualityProfiles/syncer.ts:401-416`). To satisfy “only Praxrr-created,” create a new ownership row only for a confirmed create; refresh timestamps/provenance on update only for already-owned IDs, unless an explicit adoption policy is separately approved. No historical name/suffix backfill can prove creation.
- Use the existing safe error split in `packages/praxrr-app/src/lib/server/sync/sanitizeArrWriteError.ts:17-44`: user-facing stable reason versus protected log diagnostics. A delete writer should return `action: 'delete'` with success, failed, or an explicit guard-skip outcome, preserving partial outcomes just as the normal QP syncer does (`qualityProfiles/syncer.ts:357-359,445-453`).
- Reuse `BaseSyncer`'s reviewed evidence recorder and immutable prepared context (`packages/praxrr-app/src/lib/server/sync/base.ts:122-165,178-196`). Bind ledger candidates, policy, resolved desired set, authoritative remote identity, and assignment guards into the reviewed materialization. Review binding has canonical evidence hashing and comparison (`packages/praxrr-app/src/lib/server/sync/preview/reviewBinding.ts:259-299,399-402,540-543`). Do not add a mere `previewed: true` flag or allow an ordinary scheduled sync to perform deletes just because pruning is enabled.
- **Last deselection is a real integration seam:** ordinary QP sync returns before any remote work when total selected profiles is zero (`qualityProfiles/syncer.ts:369-378`). A prune planner/executor must still handle a truly empty resolved desired set. Conversely, this early return cannot distinguish “nothing selected” from unavailable source data by itself.

### Preview, history, drift, and Canary evidence

- `diffEntityCollection` already builds delete-shaped `EntityChange`s for unconsumed current entities (`packages/praxrr-app/src/lib/server/sync/preview/sectionDiffs.ts:156-225`), but matches by namespace/name (`:148-155,172-175`). Use the common DTO/field-diff machinery; do **not** treat its unconsumed entities or tie-breaker as deletion authority. Managed delete candidates must be ledger/remote-ID qualified and separately guarded.
- `flattenSyncPreviewChanges` tags existing CF and QP preview changes into history (`packages/praxrr-app/src/lib/server/sync/syncHistory/record.ts:75-93`); failed outcomes influence run status (`:45-63`). Existing additive audit migration stores `entity_outcomes` and `preview_id` (`packages/praxrr-app/src/lib/server/db/migrations/20260720_add_sync_history_entity_outcomes.ts:19-24`). Reuse that evidence route rather than making a pruning-only audit table.
- **Do not write the ownership ledger through history recording.** History is optional and best-effort (`syncHistory/record.ts:11-13,193-212`), whereas ownership is deletion authorization. Ownership updates must remain correct when history is disabled or its insert fails.
- Drift collects preview CF/QP changes already (`packages/praxrr-app/src/lib/server/sync/drift/check.ts:204-213`), but all delete actions currently map to category `unmanaged` (`:146-164`), and notification signatures deliberately exclude deletes (`:257-273`). Managed pending prune needs explicit semantics and tests rather than silently inheriting the present “unmanaged churn” interpretation.
- Canary's durable remaining-target evidence uses `GeneratePreviewResult[]` (`packages/praxrr-app/src/lib/server/sync/canary/types.ts:59-77`), with rollout-to-sync-history correlation (`:147-164`). Feed the same managed delete preview into this existing representation; do not invent a parallel deletion evidence blob. Evidence generation alone is not proof that an eventual per-target delete received reviewed authorization.

### Migration and query patterns

- Use the app DB `Migration` object (`packages/praxrr-app/src/lib/server/db/migrations.ts:97-103`), with one SQL `up` and matching `down`. Pure SQL migration execution and registration are transactional (`:168-178`); imports and `loadMigrations()` are explicit (`:90-95,330-423`). No new migration framework or Kysely table-builder convention is necessary.
- `packages/praxrr-app/src/lib/server/db/migrations/20261023_create_arr_trash_guide_namespaces.ts:23-35` is the closest small Arr-instance-owned table example: composite identity, unique constraint, checks, and `instance_id ... ON DELETE CASCADE`. Its explanation at `:11-14` is especially relevant: provenance can intentionally survive source deletion. For the ownership ledger, a cascading database/source FK would destroy precisely the evidence needed after upstream source removal; choose noncascading/null-preserving provenance deliberately.
- Keep ledger SQL in a single typed query-object module, following `packages/praxrr-app/src/lib/server/db/queries/arrNamespaces.ts:3-7,15-25,50-66,72-78` and `arrTrashNamespaces.ts:9-17,31-39`: typed row interfaces, bound SQL parameters, read-only getters, narrow write methods. Do not scatter INSERT/DELETE SQL among syncers, routes, and cleanup.
- New per-instance policy can follow existing instance row/create/patch types and explicit SELECT/patch handling (`packages/praxrr-app/src/lib/server/db/queries/arrInstances.ts:7-68,89-136`), or a cohesive policy query module if contract design chooses a separate table. Default off belongs in the migration as well as API/UI defaults.
- Ledger persistence is app state, not a PCD base-op migration. The existing audit migration explicitly distinguishes this (`20260720_add_sync_history_entity_outcomes.ts:13`). Do not add ledger table creation to PCD `seedBuiltInBaseOps.ts`.

## Modularity Design

### Proposed small boundaries

These are recommended modules, not implemented files. Names can follow the technical design; responsibilities should remain distinct.

1. **`db/queries/arrManagedEntities.ts` — persistence only (~150–250 lines).** Row/input types; list per instance/section; confirmed-create insert; owned-update touch; confirmed-delete removal; narrow transaction helpers. Composite identity should include instance and entity kind plus remote ID; names are provenance/display, not keys for destructive authorization. Preserve first timestamp on upsert and last timestamp only after confirmed writes. Validate remote ID representation at the boundary.
2. **`sync/managedEntities/desired.ts` — desired-source resolution (~200–350 lines).** Extract existing PCD/TRaSH desired-name and unknown-source guards from cleanup into one reusable resolver. Return an explicit resolved/unknown state per source, not just empty sets. Cleanup and pruning consume it; neither reimplements source hydration or namespace rules.
3. **`sync/managedEntities/plan.ts` — pure ownership comparison (~150–250 lines).** Intersect ledger rows with authoritative current remote IDs; exclude desired IDs/source identities and unknown sources; generate immutable guarded candidates and user-readable skip reasons. No DB writes, HTTP deletes, or UI state. Build maps/sets once, retaining linear comparison rather than nested scans or repeated remote reads.
4. **`sync/managedEntities/references.ts` — explicit Arr guards (~150–300 lines).** A small `switch(arrType)` delegates to validated Radarr/Sonarr/Lidarr reference checks using existing clients. No implicit sibling fallback and no generic “HTTP 500 = assigned” classifier. Keep unsupported/missing reads fail-closed.
5. **`sync/managedEntities/write.ts` — reviewed deletion only (~150–250 lines).** Consume a revalidated prepared candidate set; call existing delete methods; emit canonical sanitized terminal outcomes; remove ownership only on confirmed success. Record successful ownership at existing create/update write seams separately; do not add broad lifecycle hooks to the base class. Both cleanup's managed mode and sync pruning should share authorization primitives, not call unguarded `deleteStaleItems` with arbitrary arrays.
6. **Existing adapters remain thin.** Cleanup request parser/route handles contract validation and explicit unmanaged mode; preview exposes managed delete changes and evidence; sync/Canary jobs use the existing reviewed execution lifecycle; history/drift consume the canonical outputs. One per-instance policy source is read in every destructive entry path.

### KISS and file-size guardrails

- The existing QP syncer ends at line 1,458 and owns both source hydration and payload writing (`qualityProfiles/syncer.ts:813-1159,1256-1408`). It is already well above the soft cap. Do not append ledger SQL, prune comparison, reference scanning, and preview guard code to it. Extract only cohesive seams needed by this feature; avoid a broad unrelated rewrite.
- Cleanup is currently 358 lines (`cleanup.ts:357-358`), base syncer 197 (`base.ts:178-197`), CF syncer 293, and migration registry 435 (`migrations.ts:432-435`). Keep cleanup below ~500 by moving shared desired resolution out rather than embedding both managed/unmanaged implementations. Keep each new test file below the same approximate cap; `cleanup.test.ts` already reaches line 732 and outcome tests line 644, so use focused ledger/planner/writer suites instead of growing them indefinitely.
- Do not introduce an ownership ORM, polymorphic entity-class hierarchy, generalized reconciliation engine, new queue type, or second preview store. The feature has two initial entity families and one destructive workflow; typed data plus small functions is sufficient.
- Maintain separate meanings: desired preview (`EntityChange`), actual write (`SyncEntityOutcome`), and persistent authorization (ledger). Sharing DTOs and helper functions is useful; conflating those states is unsafe.
- Ledger insertion must not silently adopt preexisting suffix/name matches. No backfill is the safest initial migration consistent with creation-only ownership; historical entities remain unmanaged until an explicit adoption mechanism is specified.
- Arr writes and SQLite transactions cannot be atomic together. A remote create followed by failed ledger insert should leave an unowned orphan (safe nondeletion), not infer ownership from a later update. A failed local removal after remote deletion must not cause a later ID collision to authorize deletion without current identity guards. Exact recovery policy is a technical-design decision; do not hide errors behind best-effort history recording.
- Keep snapshot scope bounded and shared across plan/evidence/writer; do not repeatedly fetch all remote CFs/QPs inside each candidate loop. Existing preview compilation already accepts captured remote CF state via a lightweight client (`qualityProfiles/syncer.ts:511-513`), demonstrating reuse of one authoritative read without a cache framework.
