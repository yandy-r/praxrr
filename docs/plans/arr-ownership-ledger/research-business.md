## Executive Summary

YAN-516 / #351 adds an **ownership ledger** (`arr_managed_entities`) recording which Arr custom formats (CF) and quality profiles (QP) Praxrr wrote, plus an **opt-in, preview-first prune** of ledger entries that are no longer desired. All paths below are under `packages/praxrr-app/src/lib/server/` unless prefixed otherwise; the research was done in the worktree.

Findings that shape the business rules:

1. **Sync identity is the exact suffixed name, never the id.** CF sync builds `existingMap = name -> id` and matches `pcdName + suffix` exactly (`sync/customFormats/syncer.ts:149,162-163,191-193`). QP sync does the same (`sync/qualityProfiles/syncer.ts:402-403,1303`). `getNamespaceSuffix` never returns `''` (index >= 1, `sync/namespace.ts:28-32`; TRaSH suffix `sync/namespace.ts:38-41`). So Praxrr cannot write, match, or "adopt" an **unsuffixed** (hand-made) entity. Adoption is only possible for a live entity whose name already equals `pcdName + exact suffix`.
2. **`delete` already exists in previews, with a different meaning.** `diffEntityCollection` emits action `delete` for **every** live Arr entity with no desired counterpart, hand-made ones included (`sync/preview/sectionDiffs.ts:211-225`). Drift reads it as non-alerting `unmanaged` (`sync/drift/check.ts:146-150`, `sync/drift/types.ts:38`), and the orchestrator counts it in `totalDeletes` (`sync/preview/orchestrator.ts:222-224`). Nothing executes it: syncers never delete, and `SyncEntityAction 'delete'` is reserved/unused (`sync/types.ts:17-19`). **A prune `delete` must come from the ledger, never from this preview `delete`.** The two must be distinguishable in preview, history, drift and canary evidence, or "delete" will mean "informational" and "will be removed" in the same list.
3. **Manual cleanup is the opposite policy.** `scanForStaleItems` treats everything not expected as stale, including unsuffixed hand-made entities (`sync/cleanup.ts:5-8,196-213`). It protects only namespaces whose expected contents cannot be determined (`keepSuffixes`, `cleanup.ts:69,82-89,150,184-187`). `executeCleanup` already re-scans server-side and requires id **and** name to match (`cleanup.ts:244-269`, YAN-471).
4. **Outcome data is thin.** `SyncEntityOutcome` carries `section, arrType, entityType, name (unsuffixed pcdName), action, status, remoteId, reason` (`sync/types.ts:46-61`). It has no `databaseId`, no source kind (pcd/trash) and no suffix, so the ledger's `database_id` and `source_kind` cannot be filled from outcomes alone. See rule B3.
5. **Unreviewed sync paths exist** that must never prune: scheduled/event syncs (`sync/processor.ts:219,380`), `executeSyncJob` (`jobs/handlers/arrSync.ts:190`), and the canary rollout (`sync/canary/coordinator.ts:62`, `jobs/handlers/canaryRollout.ts:51`). Only the reviewed path (`executeReviewedSyncJob`, `jobs/handlers/arrSync.ts:505`, with current-value guards at `sync/qualityProfiles/syncer.ts:696-743`) satisfies "always preview first".
6. **FK cascades can erase evidence.** Unlinking a database cascade-deletes `arr_database_namespaces` and `arr_sync_quality_profiles` rows (`db/migrations/047_create_arr_database_namespaces.ts:23-24`, `029_add_database_id_foreign_keys.ts:21-41`, `pcd/core/manager.ts:144-157`). The ledger must not FK-cascade on `database_id`, following the TRaSH precedent (`db/migrations/20261023_create_arr_trash_guide_namespaces.ts:5-12`). It should cascade only on `instance_id`.

Open decisions are marked **[DECISION]** and uncertainties **[UNVERIFIED]**.

### User Stories

- **U1 Operator, tidy Arr after a PCD change.** I removed a CF from my PCD (or deselected a QP), and I want Praxrr to remove only the Arr copy it created, after I review exactly what will be removed.
- **U2 Operator with hand-made configuration.** I keep my own CFs and QPs in Radarr/Sonarr/Lidarr, and I never want Praxrr to delete anything it did not create, even when it has a similar name or lacks a namespace suffix.
- **U3 Cautious operator.** Pruning is off by default per instance. Turning it on changes nothing until I run a preview and confirm. Scheduled or automatic syncs never delete behind my back.
- **U4 Operator with profiles in use.** If a QP being pruned is still assigned to movies/series/artists (or Lidarr import lists/root folders), Praxrr skips it, tells me why, and keeps the ledger row. It does not generate an Arr 500.
- **U5 Existing install.** I upgraded from a version without the ledger and already have many synced CFs/QPs. I want them protected from accidental pruning until Praxrr can prove it owns them, and I want a safe way to bring them under management.
- **U6 Auditor.** Every prune delete appears in sync history (planned change and confirmed outcome), the drift view, and canary evidence, so I can answer "who deleted this CF and when".
- **U7 Cleanup user.** The manual cleanup scan shows only Praxrr-owned stale items by default; "include unmanaged" is an explicit, clearly labelled opt-in that keeps the current behaviour.
- **U8 Multi-database / TRaSH user.** Two databases (or a PCD and a TRaSH source) define a CF with the same name. Each is a distinct Arr entity with its own suffix. Removing it from one source must not delete the other source's copy.
- **U9 Operator who renames.** I rename a QP in the PCD, and I do not want the old Arr copy silently deleted while media still uses it, or duplicated forever.

### Business Rules

Each rule is stated so it can be tested. "Code" cites the behaviour being relied on or changed.

#### A. What counts as managed

- **A1. Eligible entities.** The ledger covers only entities with a server-assigned remote id and a name identity: `entityType` `customFormat` and `qualityProfile`, section `qualityProfiles`. Singletons and bulk configs (`delayProfile`, `metadataProfile`, `naming`, `mediaSettings`, `qualityDefinitions`) are never ledger-managed and never pruned. Code: `SyncOutcomeEntityType`, `sync/types.ts:30-37`; singleton diffs `sync/preview/sectionDiffs.ts:234-300`; media subsections return `remoteId` of a config row (`sync/mediaManagement/syncer.ts:374,527`). **[DECISION]** Lidarr metadata profiles are named, namespaced entities (`sync/metadataProfiles/syncer.ts:332-340`). The issue scopes pruning to CF/QP, so they stay out of scope.
- **A2. A ledger row is written only from a confirmed success.** Only an outcome with `status === 'success'` and a non-null `remoteId` creates or touches a row. `failed` and `skipped` never write one. A `create` that failed leaves no row, and a failed `update` does not advance `last_synced_at`. Code: `writeCustomFormatPayload` `sync/customFormats/syncer.ts:93-131`; QP outcome `sync/qualityProfiles/syncer.ts:1305-1311`; skip reasons `:828-845`.
- **A3. `source_kind` distinguishes created from adopted.**
  - `created`: first confirmed `action:'create'` success with a new `remoteId` and no existing row. Prunable once it falls out of the desired set.
  - `adopted`: confirmed `action:'update'` where the live entity pre-existed (matched by the exact suffixed name) and no row existed. This is the "adopted-by-name-match" case. Because sync matches only `pcdName + exact suffix` (`sync/customFormats/syncer.ts:191-193`), an adopted entity is either a pre-ledger Praxrr write (U5) or a hand-made entity whose name collides with the suffixed form. The two are indistinguishable at write time.
  - **[DECISION, recommended fail-closed]** `adopted` rows are **not prunable** by default. They become prunable only through an explicit per-instance "claim existing" action, previewed like any other change (see F). This is the only way to honour AC2 ("hand-made never deleted") against a name collision.
  - **[DECISION]** `source_kind` is not the issue's pcd/trash split. The issue lists `source_kind` among the columns. If it means pcd/trash, an `origin` flag (`created|adopted`) is needed as well. Batches already carry `sourceKind: 'pcd'|'trash'` (`sync/qualityProfiles/syncer.ts:83`), and the TRaSH batch uses `databaseId: -source.id` (`:1098`). `database_id` for TRaSH rows needs a defined representation, either the negative id or a null with a source id column.
- **A4. Uniqueness and key.** A row is unique per `(instance_id, entity_type, remote_id)`. Several rows may share `pcd_name` when their `database_id`/suffix differ (U8). `section` is constant for CF/QP (`qualityProfiles`). The Arr type comes from the instance and is validated, never inferred (`sync/preview/orchestrator.ts:180-186`; cross-Arr policy). A ledger read or write for an instance resolves its `arr_type` explicitly, with no sibling fallback.
- **A5. Unsuffixed entities are never managed.** Sync always appends a non-empty suffix, so an entity whose full name has no trailing namespace run cannot be a ledger row. Code: `getTrailingNamespaceSuffix`, `sync/namespace.ts:58-60`; `cleanup.ts:200,211` currently treats them as stale, which is exactly what the ledger scope must exclude.
- **A6. `first_synced_at` is set once and `last_synced_at` is updated on each confirmed write.** This follows the reserved-field pattern already used for `last_synced_at` (`db/queries/arrSync.ts:1357-1384`). **[DECISION]** An unchanged entity that is not rewritten leaves `last_synced_at` untouched. The syncers write every desired CF on each run (`sync/customFormats/syncer.ts:272-290`), so in practice it is touched each run.

#### B. How sync matches Arr entities today (the matching contract the ledger must respect)

- **B1. Write path = exact suffixed name.** CF: `existingMap` is keyed by raw Arr name, `suffixedName = pcdName + suffix`, `arrFormat.id = existingMap.get(suffixedName)`, so a hit means `update`, a miss means `create` (`sync/customFormats/syncer.ts:149,162-163,191-199`, `:73,100`). QP: `existingMap` by raw name, `remoteId: existingMap.get(suffixedName) ?? null` (`sync/qualityProfiles/syncer.ts:402-403,1303`). There is no case folding and no stripped fallback on the write path.
- **B2. Preview path = `findNamespaceMatch`.** Exact first, then stripped-name match (shortest suffix wins) only if the desired name has no suffix (`sync/namespace.ts:132-186`, no-fallback guard at `:154-156`). Since every desired CF/QP name is suffixed (`sync/customFormats/syncer.ts:163`, `sync/qualityProfiles/syncer.ts:1276`), the preview's stripped branch is not taken for CF/QP. Preview and write are equivalent for them.
- **B3. Ledger writes need data the outcome lacks.** The write sites know `batch.databaseId`, `batch.sourceKind`, `batch.suffix` (`sync/qualityProfiles/syncer.ts:82-92`), but `SyncEntityOutcome.name` is the unsuffixed `pcdName` (`sync/types.ts:52`). Without a contract change (or ledger writes inside the syncers), two databases with the same CF name cannot be told apart (U8). This is a contract-level requirement, not an optional enhancement.
- **B4. Reviewed execution guards by name.** The reviewed path rebuilds `guardedCustomFormatIds` and `guardedProfileIds` (name -> id) and throws on mismatch (`sync/qualityProfiles/syncer.ts:696-705,718-720,738-743`). A prune delete in the reviewed path needs an equivalent guard keyed on `(remoteId, exact live name)`.

Additional "not desired" rules:

- **C6 Per-instance, not global.** Desired is evaluated per instance from that instance's selections and namespace table (`arrNamespaceQueries`, `db/queries/arrNamespaces.ts`). Another instance's ledger is never consulted.
- **C7 Suppress during startup pull.** While `isStartupPullInstanceActive(instanceId)` (`sync/processor.ts:42-54`), selections are being rebuilt from live Arr state (`pull/startup/applySelections.ts:64`). A transient selection set must not drive pruning.
- **C8 CF deletion follows QP deletion.** `deleteStaleItems` deletes CFs before QPs (`cleanup.ts:316-345`). The sync writes a `formatItems` entry for every CF on every profile (zero-score filler, see the comment at `sync/qualityProfiles/syncer.ts:745-748`). A CF being pruned can still carry a **non-zero** score on a QP that is kept (in use, or from another source). **[DECISION]** Do not prune a CF that has a non-zero score on any retained live QP, and report the reason, rather than silently stripping scoring from an in-use profile. **[UNVERIFIED]** Whether Radarr/Sonarr/Lidarr cascade-remove a deleted CF from `formatItems` or reject the delete. This must be checked per `arr_type`.

#### D. Identity, rename and drift of live entities

- **D1. Delete by `(remote_id, live name)`, not by name or id alone.** A prune delete executes only if the live Arr entity with that id still has a name equal to the exact expected suffixed name of the row (`pcd_name` + the suffix derived from `database_id` and the namespace). Otherwise it is skipped as "changed outside Praxrr". This mirrors the id-and-name guard in `executeCleanup` (`cleanup.ts:251-269`) and the reviewed guards (`sync/qualityProfiles/syncer.ts:718-720`). It also protects the case where the instance URL was repointed to a different server. **[UNVERIFIED]** Whether editing the instance URL clears sibling per-instance state. Namespaces are keyed only by `instance_id`.
- **D2. A user rename of the Arr entity.** If the live name no longer matches, sync creates a new suffixed entity (the old name is not found, B1), and the old row's live name fails D1. Result: **drop the row's prune eligibility (mark `lost` or delete the row), never delete the renamed entity.** It is now effectively hand-made.
- **D3. Entity deleted in Arr by hand.** If the remote id is absent from the live list, the row is stale. Remove the row, emit no delete, and do not treat it as failed.
- **D4. A rename in the PCD (QP).** The PCD rename propagates to selections by name for that database only (`db/queries/arrSync.ts:970-992`, called from `routes/quality-profiles/[databaseId]/[id]/general/+page.server.ts:151`). The next sync creates a **new** suffixed QP (new name, B1) and the old ledger row (old name) is no longer desired. Expected outcome: create new, then prune old, **blocked if the old QP is assigned to media (E)**. Users then see two profiles until media is reassigned. This is the documented consequence, not a bug.
- **D5. A rename in the PCD (CF).** No selection propagation exists for CF names. The old CF falls out of the desired set (C2) and the renamed CF is created. Same prune-after-create ordering and C8 apply.
- **D6. The same name in two sources is two entities (U8).** The suffix distinguishes databases (`sync/namespace.ts:28-41`), so pruning keys on the ledger `database_id`/suffix and never on `pcd_name` alone.
- **D7. Re-linking the same repository after unlink creates a new database id.** The old rows keep the stale `database_id` and the new namespace index differs, so the old entities are legitimately orphaned and appear as C3 deletes. They do not collide with the new ones.

#### E. QP-in-use rule

- **E1. Never delete a QP that media still uses.** At preview time Praxrr determines, per `arr_type`, whether the QP is assigned. Today's behaviour is reactive: the Arr rejects the delete with HTTP 500 and cleanup reports "Profile is assigned to media" (`sync/cleanup.ts:332-345`).
  - Radarr: movies' `qualityProfileId` (`utils/arr/clients/radarr.ts:22`, `getLibrary` joins by it at `:90`).
  - Sonarr: series' `qualityProfileId` (`utils/arr/clients/sonarr.ts:26`).
  - Lidarr: assignment lives on the artist (`utils/arr/clients/lidarr.ts:32,200-215`). `ApiResearcher-2` reports it is also referenced by import lists (wire field `qualityProfileId`) and root folders (`defaultQualityProfileId`). **[UNVERIFIED by this agent]** Each `arr_type` needs its own audited reference list; no shared helper without proof of parity.
- **E2. Result of an in-use QP.** Outcome is `skipped` (not `failed`), with a sanitized reason such as "Quality profile is assigned to media". The ledger row stays, the plan marks it blocked, and it is retried on later reviews. A 500 at execution time that was not predicted at preview time is also classified `skipped`, matching `cleanup.ts:337-343`. Other HTTP errors stay `failed`.
- **E3. The in-use check is advisory, not authoritative.** Fail closed: if the media list cannot be fetched, treat every QP as in use (skip), and do not proceed with a "best effort" delete.
- **E4. CF deletion is not blocked by usage.** CFs have no media assignment. C8 governs the retained-QP scoring dependency.

#### F. Preview-first rule

- **F1. Pruning executes only via the reviewed apply path.** A delete is allowed only inside `executeReviewedSyncJob` (`jobs/handlers/arrSync.ts:505`) for a preview that is `ready`, unexpired, and whose evidence still matches (`jobs/handlers/arrSync.ts:612-624,636-640`; apply route `routes/api/v1/sync/preview/[previewId]/apply/+server.ts:132-281`). The unreviewed paths (`processor.syncInstance` `sync/processor.ts:352-385`, `processPendingSyncs` `:271-346`, `executeSyncJob`) must never pass a "prune" capability to the syncer, so scheduled, event and canary-phase syncs never delete. **[UNVERIFIED]** `executeSyncJob` is also used by the canary rollout (`sync/canary/coordinator.ts:62`, `jobs/handlers/canaryRollout.ts:51`). Canary phase-A and phase-B syncs are unreviewed, so they would never prune. Whether canary should offer a reviewed prune is an open design decision.
- **F2. The preview shows the exact set to be deleted.** Each prune candidate appears in the preview as an `EntityChange` with action `delete`, `remoteId`, and a marker that distinguishes it from today's informational "unmanaged" deletes (`sync/preview/sectionDiffs.ts:211-225`). The prune plan is frozen into the reviewed binding/prepared context (as `desired`/`currentGuards`, `sync/qualityProfiles/syncer.ts:604-618`), so execution deletes exactly what was reviewed and revalidates the live `(id, name)` first.
- **F3. Staleness invalidates the review.** If the ledger, selections, PCD, or live Arr list changed since review, the apply returns `invalidated` and writes nothing (`jobs/handlers/arrSync.ts:412-425,600-609`; reasons `sync/preview/types.ts:20-21`). The ledger and policy state must be part of the compared evidence (`recordPreviewEvidence`, `sync/base.ts:135-142`), or a policy flip between preview and apply would pass unnoticed.
- **F4. Policy off means no delete candidates.** With "prune removed managed entities" off (default), no ledger-sourced `delete` appears in a preview and none executes. Informational unmanaged deletes remain as today. **[DECISION]** Whether the ledger is still _written_ while the policy is off. Recommended: yes, so enabling the policy later has history. Writing is harmless and always safe.
- **F5. Ordering inside an apply.** Create/update (CF, then QP) happens first, then QP deletes, then CF deletes. This guarantees a replacement exists before its predecessor is removed (D4), and a QP never references a missing CF. Each delete produces its own `SyncEntityOutcome{action:'delete'}` with `remoteId`.
- **F6. Preview cost.** Drift and history reuse `generatePreview`. A prune plan adds ledger reads and (per E1) media reads to every preview, including the scheduled drift sweep (`sync/drift/check.ts:296-415`). **[DECISION]** Compute the in-use check only for reviewed/prune previews, not for the drift sweep, or cap it with the existing rate limits (`drift/limits.ts`).

#### G. Hand-made CF/QP protection (AC2)

The deletion of an entity requires **all** of the following. Failure of any single one means keep.

1. Instance policy on.
2. A ledger row exists with `origin = created` (or claimed under F).
3. The row's `(instance_id, remote_id)` is present in the live Arr list.
4. The live name equals the expected `pcd_name + suffix` for the row's `(database_id, namespace)`.
5. The entity is positively undesired (C1-C4) and the evidence is not an error or unavailability case (C5).
6. It is part of a reviewed, unexpired, unchanged preview (F).
7. QP only: not in use (E), and CF only: not scored on a retained QP (C8).

Consequences, each testable:

- A hand-made CF with no suffix is never in the ledger (A5), never matched by sync (B1), and so never deleted by pruning.
- A hand-made CF whose name collides with a suffixed name is `adopted` and not prunable (A3).
- A ledger entity renamed in Arr fails condition 4 (D2).
- Cleanup scoped to the ledger ignores everything else (H).

#### H. Cleanup scoping

- **H1. Default scope is the ledger.** `scanForStaleItems` returns only items that are in the ledger _and_ not expected (reusing the existing expected-set machinery and its `keepSuffixes`/TRaSH fail-safes, `sync/cleanup.ts:57-230`). Unmanaged hand-made entities are never listed.
- **H2. "Include unmanaged" is an explicit mode** that reproduces today's behaviour (`cleanup.ts:196-213`). The mode is part of the request contract (`sync/cleanupRequest.ts:366-367`, currently `{action, instanceId[, scanResult]}`) and of the OpenAPI schema (contract-first).
- **H3. Execute re-scans in the same mode.** `executeCleanup` re-scans server-side and deletes only the intersection of the requested items with the fresh scan (`cleanup.ts:244-300`, YAN-471). The mode must be re-derived server-side from the request, and a client cannot widen a ledger-scoped scan into an unmanaged one by replaying ids.
- **H4. Cleanup deletes should also update the ledger.** A successfully deleted ledger entity removes its row and produces a `delete` outcome. **[DECISION]** whether cleanup (manual, not part of a reviewed sync) records sync-history rows. Today it does not (`cleanup.ts` has no history calls), but AC3 asks for delete outcomes to appear in history. Prune deletes definitely do (F). Cleanup is a recommended addition.

#### I. Backfill for existing installs (U5)

- **I1. Do not guess ownership.** There is no durable record of which entities were created (TRaSH `last_synced_at` is not reliably written and history is pruned, see the comment at `sync/qualityProfiles/syncer.ts:1142-1151`). A migration cannot call the Arr, and the app DB has no remote ids. Therefore **the migration creates the table empty**, with no backfill and no ledger rows. This follows the precedent of `20261023_create_arr_trash_guide_namespaces.ts:15-16` ("No backfill").
- **I2. First sync after upgrade.** Existing suffixed entities arrive as `action:'update'` with no row, so they become `adopted` (A3) and are **not prunable**. This is safe by default: an upgrade alone can never delete anything.
- **I3. Claiming.** To make adopted entities prunable, the operator uses an explicit, previewed, per-instance "claim" that lists candidate adopted rows, namely those whose live name carries the exact current namespace suffix for a known `(instance, database)` (`sync/namespace.ts:58-60`; `arrNamespaceQueries.getForInstance`, `db/queries/arrNamespaces.ts:64`). Claiming flips `origin` to `claimed`. **[DECISION]** The simpler option is auto-claim for rows that were `update`d by a sync whose full name has the exact suffix. That is correct for Praxrr-written entities but cannot be told apart from a colliding hand-made name. The explicit claim keeps AC2 absolute.
- **I4. Startup pull is not ownership.** The pull builds selections by matching live names to local profiles via namespace strip (`pull/startup/profileMatching.ts:127-168`). A match there is a _selection hint_, not proof Praxrr wrote the entity, so it must never create ledger rows.
- **I5. No retroactive history.** Backfill never fabricates `first_synced_at` for adopted rows beyond the first observed sync.

#### J. Policy

- **J1. Per instance, default off.** The policy is stored per instance (`instance_id`), defaults to off, and is changed through a contract-first `/api/v1` endpoint with OpenAPI first. Deleting the instance cascades its policy and ledger (`arr_instances` FK).
- **J2. Policy per `arr_type` is validated.** Enabling is rejected for any instance type without a verified in-use rule (E1), so no implicit sibling fallback occurs.
- **J3. Turning the policy off does not delete ledger rows.** Rows remain so re-enabling resumes from accurate ownership. Turning it on requires no immediate action and prunes nothing until a reviewed preview is applied.

#### K. Evidence and observability (AC3)

- **K1. Sync history.** Delete outcomes ride existing plumbing: `SyncEntityAction` already includes `delete` (`sync/types.ts:19`), history stores `entity_outcomes` JSON plus a count (`db/migrations/20260720_add_sync_history_entity_outcomes.ts`), the UI already labels it "Deleted" (`lib/client/ui/sync-history/syncOutcomeStatus.ts:25`), and the planned `changes` come from `flattenSyncPreviewChanges` (`sync/syncHistory/record.ts:86-123`). **[DECISION]** `deriveSyncHistoryStatus` (`record.ts:45-64`) must treat a skipped-in-use prune as non-failing, otherwise a policy-on instance would show `partial` forever.
- **K2. Drift.** Drift currently classifies all `delete` as `unmanaged`, non-alerting, excluded from `driftSignature` (`sync/drift/check.ts:146-150,263-274`). AC3 requires prune deletes to appear in drift. **[DECISION]** Surface "pending prune" as a distinguishable category or flag. Do not silently make them alerting, since that would change notification dedup semantics. The `DriftEntityChange.action` union already contains `delete` (`sync/drift/types.ts:51`).
- **K3. Canary.** Remaining-target preview evidence carries full `GeneratePreviewResult`s (`sync/canary/coordinator.ts:141-233`), and persisted canary decoding already accepts `delete` and `totalDeletes` (`db/queries/canaryRollouts.ts:235,302`). Prune deletes therefore flow through if they are `EntityChange`s in the preview. A new `EntityChange` marker/field must be added to the canary decoder, which validates shapes strictly (`canaryRollouts.ts:228-262`).
- **K4. Outcome contract extension.** Persisted/API outcomes will gain `delete` entries with `remoteId`. Any OpenAPI enum or schema for outcomes and preview actions must be checked for `delete` already being listed (`lib/api/v1.d.ts` mentions outcomes). **[UNVERIFIED]** I did not diff the OpenAPI schema.

#### L. Failure and safety behaviour

- **L1. A failed delete never removes the ledger row.** Only a confirmed delete (2xx or an already-gone 404 - **[DECISION]**) removes the row.
- **L2. Partial failure is isolated.** One failed delete does not abort the others. Each yields its own outcome (pattern: `deleteStaleItems`, `cleanup.ts:316-345`). The sync history status becomes `partial`.
- **L3. Concurrency.** The reviewed path claims the sections before any write (`claimReviewedSyncSections`, `db/queries/arrSync.ts:1340`), so a prune cannot overlap another sync of the same instance. Cleanup has no such claim today. **[DECISION]** cleanup execute on a ledger-scoped delete should also take the section claim or at least re-validate (it re-scans, so it is already guarded for staleness but not for a racing sync that is about to re-create).
- **L4. Logging.** Sanitize Arr error bodies (`sync/sanitizeArrWriteError.ts`) in delete outcomes, as in create/update (`sync/customFormats/syncer.ts:107-117`).
