## Executive Summary

YAN-516 / #351 is mostly a **re-use-and-extend** UX job: every surface the feature needs already exists (preview panel with a typed-confirmation destructive modal, confirmed-outcome list with a `Deleted` label, drift `unmanaged` category, canary planned-delete totals, cleanup modal with a scan→preview→execute state machine). The work is to (1) add one persisted per-instance policy control, (2) make the preview's `delete` entries mean _only_ "ledger-owned and no longer desired", (3) teach the cleanup modal a scope switch, and (4) surface "skipped — in use" and "fail-closed" states honestly. All paths below are relative to `packages/praxrr-app/src/` in the worktree.

Key findings (grounded):

1. **A latent mismatch must be fixed first.** Today the preview already emits `action: 'delete'` for _every_ live Arr CF/QP that has no desired match (`lib/server/sync/preview/sectionDiffs.ts:211-225`, fed by the unfiltered `allArrCustomFormats`/`allArrProfiles` at `lib/server/sync/qualityProfiles/syncer.ts:491-496,573-596`). The sync never executes those deletes, yet `SyncPreviewPanel.svelte` already shows a red "Destructive changes detected" banner (`:801-811`), switches the modal to "Confirm Destructive Preview Apply / Apply Deletions" with a type-the-instance-name gate (`:965-1017`), and `drift/check.ts:146-149` classifies them as non-alerting `unmanaged`. Once pruning exists, an un-scoped preview would show hand-made CFs as "Planned delete" while prune is off (misleading) and — worse — with prune on, mix real deletes with unmanaged noise. **Recommendation:** the preview must separate three things visually and in data: _planned delete (will be pruned)_, _unmanaged on instance (never touched)_, and _kept: in use_. Today's un-owned `delete` rows should be re-labelled/re-typed (e.g. a new `EntityChange` annotation, `unmanaged`) rather than reuse `delete`. [INFERENCE: I did not execute a preview to confirm the banner appears for hand-made CFs; derived from code at the cited lines.]
2. **Toggle location (as implemented):** the prune policy lives in the instance **Settings** page, not the sync page: `routes/arr/components/InstanceForm.svelte` (the `Prune removed managed entities` `Toggle`, bound to `pruneRemovedManaged` and posted as the hidden `prune_removed_managed` field) persisted by the settings form action in `routes/arr/[id]/settings/+page.server.ts`. It is a per-instance policy (`arr_instances.prune_removed_managed`), so it rides the existing instance Save flow and dirty tracking rather than the `qualityProfiles` section's `savedState`/`isDirty` machinery. The earlier recommendation to place it on `/arr/[id]/sync` in `QualityProfiles.svelte` is superseded; sections below that describe the sync-page placement are retained as design history only.
3. **Cleanup UI** lives in `routes/arr/components/CleanupModal.svelte` (253 lines), opened from the `Cleanup` button in `routes/arr/components/InstanceForm.svelte:456-461` (modal mount `:729-732`) — i.e. the instance **settings** page (`routes/arr/[id]/settings`), _not_ a dedicated route. Add a scope control inside the modal (default "Managed by Praxrr"; opt-in "Include unmanaged (hand-made)"), with an elevated typed confirmation only for the unmanaged scope.
4. **Delete outcomes in history/drift/canary** need near-zero new UI: `lib/client/ui/sync-history/syncOutcomeStatus.ts:21-26` already maps `delete`+`success` → "Deleted"; `SyncOutcomeList.svelte:58-60` already renders it; the sync-history detail (`routes/sync-history/[id]/+page.svelte:221-241`), preview-apply result (`SyncPreviewPanel.svelte:921-943`) all use that list. Gaps: the list has no visual weight for deletes (neutral/success green), no per-action filter/count, and no "kept: in use" label; `SyncHistoryDiff.svelte` and `routes/canary/[id]/+page.svelte` show only _planned_ delete counts, and the canary page has no confirmed-outcomes list at all (it renders section-level `diagnostics.sectionResults` only, `:287-323`).
5. **QP-in-use skip** has a precedent string, `'Profile is assigned to media'`, produced by mapping Arr HTTP 500 (`lib/server/sync/cleanup.ts:337-343`). The ledger feature should skip _before_ the delete (per the spec) and report a `skipped` outcome with a stable, user-facing reason; UI copy below.

### Core User Workflows

### W1 — Enable pruning on an instance (opt-in, default off)

**Location:** `QualityProfiles.svelte`, a new bordered row between the paginated profile grid (`:600-624`) and `<SyncFooter>` (`:627`). Extract as a new component `routes/arr/[id]/sync/components/PruneRemovedPolicy.svelte` (props: `checked` (bind), `disabled`, `ledgerCounts: {customFormats:number; qualityProfiles:number} | null`, `arrLabel`) to keep `QualityProfiles.svelte` (645 lines, already over cap) from growing; mount it with `bind:pruneRemoved`.

Copy (Arr-specific, no cross-Arr shortcut; `arrLabel` = Radarr/Sonarr/Lidarr from `data.instance.type`):

- Label: **"Prune removed managed items"** (Toggle `ariaLabel="Prune custom formats and quality profiles that Praxrr created on this {arrLabel} instance once they are removed from your databases"`).
- Helper `<p class="text-xs text-neutral-500">`: "When on, custom formats and quality profiles that Praxrr created here — and that are no longer in your selections or databases — are deleted from {arrLabel} on sync. Items you created by hand are never touched. Every prune is shown in a preview first. Quality profiles still assigned to media are kept."
- Status line (from ledger): "Praxrr currently manages **N** custom formats and **M** quality profiles on this instance." When ledger is empty: "Nothing is recorded as Praxrr-managed yet. Pruning starts working after the next successful sync." (this is the cold-start/empty state; do **not** imply that existing pre-feature items are managed — they are _unmanaged_ until re-synced and recorded).

Behavior:

- `on:change` sets `pruneRemoved`; enabling from off→on is a **dirty change** — fold it into `buildCurrentState(...)` (`QualityProfiles.svelte:122-152`) so `isDirty` flips, `Save` enables, `Sync Now` disables ("Save changes before syncing", `SyncFooter.svelte:42-43`) and `previewEnabled` becomes true (`:248-256`). No separate save button; consistent with the rest of the section.
- Persist through the existing `saveQualityProfiles` action: add `formData.set('pruneRemoved', pruneRemoved ? '1' : '0')` at `QualityProfiles.svelte:463-466`; parse in `+page.server.ts:515-564`; `data.syncData.qualityProfiles.config` carries the initial value (read at `+page.svelte:79-81`, pass through like `lastSyncedAt`). Contract-first: if this goes through `/api/v1`, OpenAPI first; the form action is the existing precedent for this page.
- Enabling shows an **inline amber note** (not a modal; the destructive gate is the preview/apply) using the existing `warning` mechanism style (`SyncFooter.svelte:78-83`): "Pruning is on. Your next sync will delete items removed from your selections. Use Preview Sync to see exactly what will be removed."
- First-ever enable with a non-empty selection set but empty ledger: show the empty-state copy above — never a scary banner.
- Turning pruning **off** is non-destructive: no confirmation; `alertStore.add('info', 'Pruning disabled. Previously recorded managed items stay recorded.', undefined, undefined, {key:'prune-policy'})`.
- Disabled states: the toggle is `disabled={saving || syncing || liveStatus==='in_progress'}`; if the section has **no** selections (`totalSelectedCount===0`, `:246`), still allow toggle but show the warning "No quality profiles are selected — with pruning on, a sync would remove every managed item." This is the highest-risk scenario (user deselects everything → mass prune) and needs explicit copy and, recommended, an additional server-side "mass-prune guard" (see Feedback).

Placement note: the policy is implemented on the instance Settings page (`InstanceForm.svelte`), next to the Cleanup action, as a per-instance setting. The sync-page placement described in this section was the original recommendation and is superseded; `SyncFooter.svelte` is shared by Media Management, Delay and Metadata (which have no prunable entities), which remains the reason not to put it in the footer.

Also update the "How Sync Works" `InfoModal` (`+page.svelte:538-622`) with a "Pruning" paragraph (mirrors the existing Namespacing/Automatic Dependencies blocks, `:540-557`).

### QP-in-use skip messaging

Source of truth: skip must be decided **server-side before the delete** (spec: "skip QPs that media is still assigned to"); legacy path only discovers it via HTTP 500 → `'Profile is assigned to media'` (`cleanup.ts:337-343`). Per-Arr verification: media assignment is Radarr movies / Sonarr series / Lidarr artists — `[INFERENCE]`; the cross-Arr policy requires the API researcher to verify each, and UI copy must be generated from the explicit `arrType` (e.g. "movies" for Radarr, "series" for Sonarr, "artists" for Lidarr), never a shared noun. Use `resolveEntityLabel`-style per-Arr maps (`lib/shared/narration/templates.ts:121`) for this.

Wording (preview row, status badge `neutral`/`warning`, `Badge` icon `AlertTriangle`):

- Preview: "**Kept** — still assigned to {N} {movies|series|artists} in {Arr}. Praxrr will not delete it. Reassign or remove those items' profile, then prune again."
- Outcome (`SyncEntityOutcome` status `skipped`, action `delete`): `reason` = "Kept: assigned to media in {Arr}" — `syncOutcomeLabel` already returns "Skipped" for any skipped (`syncOutcomeStatus.ts:15-17`) so the row reads `Skipped · <name> · qualityProfile · #id · Kept: assigned to media`. Recommend a distinct label "Kept (in use)" for `action==='delete' && status==='skipped'` (small change to `syncOutcomeLabel`) so it is not confused with "unsupported field" skips.
- A kept profile **stays in the ledger** (it is still Praxrr-created) so the next prune re-evaluates; UI hint in the helper under the outcome: "It will be pruned automatically once nothing uses it."
- Counts: summary chip "N kept (in use)"; it must not contribute to `totalDeletes` (so the typed confirmation is not demanded for items that will not be deleted).
- Ordering dependency: CFs referenced by a kept QP must also be kept (deleting a CF that a kept QP scores would break the profile). UI: show CF row as "Kept — used by profile '{name}' that is being kept" (info). Flag to Tech.

### Error / empty states (copy catalogue)

- No ledger yet: "Praxrr hasn't recorded any managed items on this instance yet. Run a sync, then pruning and managed cleanup will apply."
- Ledger read failed: "Couldn't read Praxrr's record of managed items. No deletions were planned." (fail closed; `Badge variant="warning"` coverage partial.)
- Arr unreachable during prune evaluation: reuse existing connection error handling (`SyncPreviewPanel.svelte:678-686`), add recovery "Check {Arr} connectivity and generate a new preview."
- Mass-prune guard: if the delete set ≥ N (e.g. 50% of ledger entries of a kind, or > 20) show an extra `role="alert"` in the apply modal "This will remove **{k} of {m}** managed items. If this is unexpected, check your database connection and selections." Rationale: a transient PCD cache failure shouldn't turn into a mass-delete; the existing cleanup code has fail-safe kept namespaces for undeterminable PCD data (`cleanup.ts:1-9,84-95`) — preview/apply must reuse that, and the UI must show _why_ items were kept ("Kept: database cache unavailable"), parity with cleanup's warnings.
- Cleanup not-found/unauthorized: `alertStore`/modal error path exists (`CleanupModal.svelte:127-137`); keep, but also show scope-specific text.
- Hand-made CF in the way: if an Arr CF with the same name as a desired entity exists but is **not** in the ledger (unmanaged), sync updates it today by name match (namespace-aware matching, `sectionDiffs.ts:151-155`). Out of scope for pruning UI, but the ledger will then record it as managed once synced — surface in the entity row: "Adopted existing item on first sync" (open question: adoption vs. refusing to take over hand-made items; AC2 "CFs created by hand are never deleted" interacts with this — if sync updates a hand-made CF named like a PCD CF, the ledger would claim it. Flag to Business/Tech.)
