## Executive Summary

Praxrr already has HTTP DELETE methods for custom formats (CFs) and quality profiles (QPs), inherited by Radarr, Sonarr and Lidarr clients; the missing capability is safe ownership/review orchestration, not a new deletion transport. All three upstream APIs expose single-entity DELETE routes, but QP dependency checks differ: Radarr blocks movies, import lists **and collections**; Sonarr blocks series and import lists; Lidarr blocks artists, import lists **and root-folder defaults**. A media-only usage scan is therefore insufficient. Recyclarr demonstrates durable source-ID → remote-ID tracking and default-off deletion of previously synchronized resources, but its same-name adoption is weaker than the issue's “Praxrr created” requirement. Configarr's `delete_unmanaged_custom_formats` is deliberately a broad name allowlist, not an ownership ledger, and must not be copied for pruning.

Research performed 2026-10-22 from primary upstream documentation/source, including released Arr tags. No live DELETE requests, builds or tests were run. Runtime observations are not claimed; status behavior below is source/OpenAPI evidence. **Lidarr naming trap:** the server domain model calls an import-list assignment `ProfileId`, but `ImportListResourceMapper` deliberately maps it to API `QualityProfileId`. Do not search for JSON `profileId` in import-list responses. Album `profileId` is a different concept in Praxrr's existing library projection, and is not a substitute for scanning the artist-level assignment required by the upstream QP delete guard.

Recommended behavior: record blocker category, count and example names in preview; skip the QP if any category references it. Re-read relevant dependencies immediately before execution. If any mandatory endpoint fails, is unsupported or returns an unrecognized shape, mark the usage assessment unknown and do not delete. The Arr delete guard remains a race backstop, not the preview implementation; never automatically reassign media, import lists, collections or root folders just to enable deletion.

#### CF deletion side effects

There is no analogous “QP is scoring this CF” veto. Arr removes the CF from quality-profile score lists when deleting it. Radarr's `CustomFormatService.Delete` publishes `CustomFormatDeletedEvent` before deleting the row; its QP handler removes the format entry from **all** profiles, and resets score thresholds if no formats remain ([service](https://github.com/Radarr/Radarr/blob/56f6168bb6f254c9a34d0e5da76040dcb4215d3d/src/NzbDrone.Core/CustomFormats/CustomFormatService.cs), [handler, lines 105–121](https://github.com/Radarr/Radarr/blob/56f6168bb6f254c9a34d0e5da76040dcb4215d3d/src/NzbDrone.Core/Profiles/Qualities/QualityProfileService.cs#L105-L121)). Sonarr and Lidarr have the same format-removal event handler pattern ([Sonarr, lines 186–203](https://github.com/Sonarr/Sonarr/blob/b3d4bb8c18f7feb6744a6cd3231279a45351bb5e/src/NzbDrone.Core/Profiles/Qualities/QualityProfileService.cs#L186-L203), [Lidarr, lines 169–185](https://github.com/Lidarr/Lidarr/blob/aec88028d036707619baacbbb840b30c2d716318/src/NzbDrone.Core/Profiles/Qualities/QualityProfileService.cs#L169-L185)). Consequently, deleting an owned CF may change scores on a manually maintained QP without deleting that QP. Preview should expose this native side effect; “delete only owned entities” must not be presented as “no effect on unmanaged profiles.”

### Integration Patterns

#### Recyclarr: tracked previously synchronized resources, default-off pruning

Primary documentation: [Custom Formats](https://recyclarr.dev/reference/configuration/custom-formats/) and [Sync State](https://recyclarr.dev/guide/troubleshooting/state/).

- `delete_old_custom_formats` defaults to **false**. When true, deleting a configured CF reference or upstream guide resource removes its synchronized Arr counterpart; manual CFs outside the configured/synchronized set are not deleted.
- Durable state maps `TrashId`, `Name`, `ServiceId` ([mapping record](https://github.com/recyclarr/recyclarr/blob/1a436908e8a57c64d5075728c00cb28272526c65/src/Recyclarr.Core/SyncState/TrashIdMapping.cs)). Legacy field aliases support old `CustomFormatName`/`CustomFormatId` cache data; it is now called sync state rather than merely cache.
- The [transaction phase](https://github.com/recyclarr/recyclarr/blob/1a436908e8a57c64d5075728c00cb28272526c65/src/Recyclarr.Cli/Pipelines/CustomFormat/PipelinePhases/CustomFormatTransactionPhase.cs#L51-L80) selects deletion candidates only from stored mappings absent from the current planned set and still present by remote ID. It explicitly avoids deleting an orphan mapping's service ID if another active managed CF claims that same ID.
- [Persistence, lines 23–46](https://github.com/recyclarr/recyclarr/blob/1a436908e8a57c64d5075728c00cb28272526c65/src/Recyclarr.Cli/Pipelines/CustomFormat/PipelinePhases/CustomFormatApiPersistencePhase.cs#L23-L46) creates, updates, conditionally deletes by stored `ServiceId`, then updates/saves state. [Mapping-store Update](https://github.com/recyclarr/recyclarr/blob/1a436908e8a57c64d5075728c00cb28272526c65/src/Recyclarr.Core/SyncState/TrashIdMappingStore.cs) retains still-existing mappings outside config when not deleted, so turning pruning on later can still discover removed resources.
- Cached ID wins over name when found. Without a valid stored ID, a unique case-insensitive name match is automatically adopted; multiple name matches are rejected as ambiguous ([transaction phase, lines 90–164](https://github.com/recyclarr/recyclarr/blob/1a436908e8a57c64d5075728c00cb28272526c65/src/Recyclarr.Cli/Pipelines/CustomFormat/PipelinePhases/CustomFormatTransactionPhase.cs#L90-L164)). Recyclarr's “manual CFs will not be deleted” guarantee therefore excludes a manual CF subsequently adopted through configuration.
- State is scoped by the complete `base_url`. Changing hostname, port, path, scheme or even trailing slash starts fresh state; docs describe subsequent name-based automatic adoption. Praxrr should use stable `instance_id`, but recognize that editing an instance to point at a different Arr database makes its old remote IDs unsafe.

Transferable pattern: durable mapping + desired-set subtraction + opt-in deletion + keep ownership while policy is off. **Do not transfer automatic adoption into deletion eligibility.** “Praxrr created” needs confirmed creation provenance, not only a later update or unchanged/name match. Existing hand-made entities updated by a name-matching sync should remain non-prunable unless a separately specified explicit ownership-transfer contract is introduced; none is required by this issue.

#### Configarr: unmanaged deletion is an intentionally broader operation

Primary docs: [configuration reference](https://configarr.de/docs/configuration/config-file/) (`delete_unmanaged_custom_formats`, since v1.12.0), and [implementation at e4909a0](https://github.com/raydak-labs/configarr/blob/e4909a0abaeded57485ecf6b5f04f492910e7974/src/arr/mediaPipeline.ts#L228-L262).

- With `enabled: true`, the pipeline builds a name allowlist from the currently resolved configured CF definitions, adds names in `ignore`, and deletes **every remote CF whose name is not in that allowlist**. Membership is ordinary JavaScript `Map` string equality, not durable remote-ID ownership.
- It emits delete diff entries and supports `DRY_RUN`; however, dry-run is not a server-enforced reviewed-plan token. Operators can run directly with deletion enabled.
- A manually created CF outside config/ignore is eligible. An upstream rename leaves the old name eligible for deletion. An unresolved configured ID cannot add its CF name to the keep-map, so the deletion block alone cannot distinguish “definition unavailable” from “no longer desired.” This is an implementation-level hazard, not a claim that every upstream failure reaches this block.
- [CF management](https://github.com/raydak-labs/configarr/blob/e4909a0abaeded57485ecf6b5f04f492910e7974/src/customFormats/customFormats.ts#L27-L104) matches existing CFs by name for update/create; it does not establish creation-only provenance. Its server cache is a working resource snapshot, not evidence that Configarr created each resource.

Transfer only the separation of delete diff calculation from mutation and the opt-in configuration shape. Configarr's broad behavior belongs, at most, to Praxrr's separately explicit “include unmanaged” cleanup mode; it is disallowed as the pruning/default-cleanup algorithm.

#### Recommended integration contract for this feature

1. **Build candidates from authoritative ownership, not remote complement.** Candidate remote IDs are ledger-owned IDs minus the union of all still-desired producers for that instance/entity family. Database/section scope matters: deselecting one source must not delete an entity still desired by another. A missing/failed desired-state read is not an empty desired set.
2. **Record confirmed remote identity.** Use the actual returned remote ID for successful creates. Do not populate destructive ownership by name-matching current Arr entities or by indiscriminately replaying every historical update outcome. Preserve first-sync provenance and keep the ledger even while pruning is disabled.
3. **Require the existing Praxrr reviewed preview before dispatch.** Arr APIs have no review binding. Bind exact candidate IDs, ownership/provenance, desired-state inputs, instance identity and relevant dependency observations into the reviewed plan; a policy toggle alone cannot authorize deletion. A scheduled/background sync may propose deletions but must not execute an unreviewed plan.
4. **Use Arr-specific preflight and fail closed.** Implement the full usage matrix above. Do not use `arr_type` sibling fallbacks. A newly observed blocker yields skipped/not-deleted evidence; a changed plan or uncertain identity requires fresh review, not opportunistic substitution of another ID.
5. **Commit evidence after remote confirmation.** Successful DELETE outcomes need remote ID, original entity/source context and action `delete`, consumable by sync history, drift and Canary. An “already absent” reconciliation must be distinguishable from a DELETE actually performed; timeout/transport failure must not be recorded as confirmed deletion or authorize name-based retries.
6. **Refresh native dependent state after CF deletion.** Re-fetch profiles before sending later QP updates so stale score arrays do not reintroduce removed CF IDs. Include Arr's score-list side effects in preview/Canary evaluation, not just a count of deleted CF objects.
7. **No new external dependency is needed.** Existing clients and SQLite persistence suffice. Contract-first Praxrr API/schema changes should expose policy, review/delete evidence and explicit unmanaged cleanup scope, while keeping Arr credentials server-side.

#### Uncertainties to preserve in implementation planning

- Upstream source and generated OpenAPI do not replace deployment tests. Exact success/no-body behavior, missing-ID DELETE handling and supported historical Arr versions still need targeted contract tests; do not hardcode the assumption that every nonexistent ID responds 404.
- Arr offers no shared transaction with Praxrr and no ownership primitive in these resources. Remote success followed by local persistence failure is a real consistency window; the implementation needs an explicit reconciliation outcome instead of claiming atomic deletion.
- Stored numeric IDs alone do not prove identity after Arr restore/replacement. Endpoint repointing/reset detection and reviewed before-state validation must prevent an old ledger ID deleting a different installation's hand-made entity.
- The proposal lists `pcd_name` rather than a stable PCD entity ID. Rename vs removal and shared-name/multi-database ownership must be specified by the technical design; Recyclarr's stable TRaSH ID cannot simply be assumed to exist in Praxrr's source model.
