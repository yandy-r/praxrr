# PCD Export/Import Atomicity: Practices Research (YAN-463, YAN-466)

## Executive Summary

- YAN-463 and YAN-466 fixes do not need new infrastructure: `db.transaction()`, YAML serializer/converter stack, and mock-heavy `importBaseOps` test seams already exist.
- Cleanest KISS path: skip/reconcile exported base ops in orphan check rather than routing drafts through YAML; replace row-by-row snapshot/restore with `db.transaction()` or savepoints.
- Draft exported rows currently untestable through public import seam (reader mocked at `entities/`, not `ops/`); any fix must add focused regression tests through existing `__testOnly_*` seams.

## Modularity Design

- Current layering is sound: `importBaseOps` (orchestration) → `writer` (persistence) → `pcdOpsQueries` (SQL) → `compiler` (cache swap). Keep it; do not add an export/import coordinator module.
- YAN-463 belongs in one of two existing seams, not a new abstraction:
  - Option A (smallest): `markBaseOrphaned` call site in `importBaseOps.ts:535` excludes just-exported filenames, or exporter tags rows so the predicate skips them.
  - Option B (larger): `exportDraftOps` writes through `converter.ts` serializers into `entities/` instead of only `ops/*.sql`, making export output import-readable by construction.
- YAN-466 belongs in persistence, not orchestration: move atomicity into `writeOperationsFromSqlOperations` (one `db.transaction` around the per-operation loop) or wrap the import loop's writer phase; delete or demote `restoreBaseRepoOpsFromSnapshot` to a fallback.
- `ENTITY_OP_FILENAME_PREFIX='entities/'` vs `EXPORTED_SQL_DIR='ops'` split is the architectural smell: two write paths, one read path. Fix by converging on one (prefer making orphan logic aware of `ops/`, not by teaching import to parse timestamped SQL dumps).
- Do not generalize `RepoOpIndex` or `consumeRepoImportIdentity` for exported drafts; both are keyed to `entities/` filenames and stable identities. A draft-specific exclusion list passed to `markBaseOrphaned` is enough.

## KISS Assessment

- **YAN-463 — exclude-from-orphan (KISS winner).** One predicate change or one exclusion parameter on `markBaseOrphaned`; ~5 lines; no YAML, no new file formats, no import-parser changes. Risk: exported row stays `published/repo` without upstream YAML — next real import must still reconcile it (define: refresh overwrites it, or export also stages a YAML placeholder).
  - Runner-up — exporter writes YAML: reuses `serialize*` + `formatDeterministicYaml`, fixes round-trip structurally, but drags in slug collisions, overwrite policy, per-entity failure handling (`converter.ts` report logic), and cross-Arr naming policy. 10x surface for same bug.
- **YAN-466 — `db.transaction()` (KISS winner).** SQLite is fully synchronous here via `@jsr/db__sqlite`; writer loop + `supersedePriorUserOps` + history inserts are plain `db.execute` calls on one connection — one `BEGIN/COMMIT` makes partial state impossible. Delete ~30 lines of snapshot/restore instead of maintaining field-by-field copy (which already risks drift: any new `pcd_ops` column must be added to `restoreBaseRepoOpsFromSnapshot:416-430` manually).
  - Caveat: verify no `await` between `BEGIN` and `COMMIT` yields to concurrent `processBatches`-style work on same connection (see non-reentrancy warnings above); import loop is sequential, writer awaits only logger/cache validation — likely safe, but assert with a concurrency test.
  - Alternative — savepoints per candidate: only if per-entity partial success must be skippable (current code throws on first failure, so full-transaction semantics already match intent; savepoints add complexity for no behavior change).
- **Do neither:** keep snapshot/restore _and_ add YAML export — two bespoke mechanisms where two stdlib/one-line mechanisms (`WHERE filename NOT IN (...)`, `BEGIN/COMMIT`) suffice.

## Abstraction vs Repetition

- Do not abstract exporter/importer into shared "op sync" interface: one writes timestamped SQL audit dumps, other reads curated YAML entities; unification would be a false symmetry.
- Do not wrap `db.transaction` in a PCD-specific helper; call it directly like `migrations.ts` and `pluginRegistry.ts` do.
- Accept small repetition: passing `excludeFilenames`/`seenAt` through `markBaseOrphaned` duplicates filename knowledge in two files — cheaper than a shared registry module for one predicate.
- If YAML export is chosen despite advice, reuse `ENTITY_SERIALIZERS` + `formatDeterministicYaml` verbatim; do not write per-entity export formatters in `exporter.ts`.

## Interface Design

- Minimal YAN-463 interface: `markBaseOrphaned(databaseId, seenAt, excludeFilenames?: readonly string[])` or exporter sets `last_seen_in_repo_at = exportedAt` _and_ import passes its own `seenAt > exportedAt` — but clock skew makes explicit exclusion safer than timestamp comparison.
- Minimal YAN-466 interface: no signature change; wrap inside `writeOperationsFromSqlOperations` or around the `withScopedCache` writer loop in `importBaseOps.ts:474-530`.
- Keep `__testOnly_*` injection style for any new seam (module-level `let fnForTests` + set/reset pairs); matches existing test files and avoids DI framework.
- Preserve `ImportBaseOpsResult { imported, orphaned }` shape; orphan count semantics change slightly under exclusion (document: exported drafts no longer counted as orphaned).

## Testability Patterns

- `importBaseOps.test.ts` patterns to copy: `patch()` helper for query monkey-patching, `fakeCache/absentCache/presentCache` stubs, `buildCandidate()` with injectable `deserialize`, per-test `__testOnly_set*/reset*` pairs.
- `writer.test.ts` pattern: real in-memory `Database(':memory:')` + `setCache(databaseId, stub)` for gate logic without app DB; extendable to transaction rollback assertions.
- Missing seams (add with fix):
  - YAN-463 regression: seed a `published/repo` op with `filename='ops/123.foo.sql'`, run import with empty candidates, assert it is _not_ orphaned (currently orphans). Requires either real `pcdOpsQueries` against test DB or exposing filename filter for assertion.
  - YAN-466 regression: inject a `deserialize` that throws on 2nd candidate, assert zero new/changed `pcd_ops` rows post-failure (transaction) vs current snapshot-restore behavior. Existing rollback tests cover compile-failure path only, not mid-loop writer failure.
- Runner gap: no `deno task test pcd` alias; run `deno task test packages/praxrr-app/src/tests/pcd/ops` explicitly. Consider adding a `pcd` alias when touching this area (one-line change in `scripts/test.ts`).

## Build vs Depend

- Nothing to install. SQLite transactions, YAML serializers, deterministic formatter, git helpers all in-repo.
- `convertCompiledCacheToEntities` is the closest thing to an "export YAML writer" dependency — reuse, don't rebuild, if YAML export path is taken.
- `getMaxOpNumber` via `git ls-tree HEAD ops/` is export-only numbering; import must never depend on it (already doesn't).

## Open Questions

1. Should exported drafts remain `source='repo'` at all, or should exporter tag them `source='local'`/distinct so the orphan predicate (`source='repo'`) skips them naturally?
2. If exclude-from-orphan wins, what reconciles the exported SQL row when the real upstream YAML later arrives — refresh-by-stable-identity overwrite, or does the `ops/` row linger forever?
3. Is `db.transaction()` reentrancy-safe on the import path (any concurrent `processBatches` or nested `withRepoImportWriteContext` `BEGIN`), or must writer use savepoints?
4. Does `restoreBaseRepoOpsFromSnapshot` stay as defense-in-depth after transactions land, or is it deleted to avoid two competing rollback mechanisms?
5. Should `scripts/test.ts` gain a `pcd` alias now that this area has dedicated regression tests incoming?
