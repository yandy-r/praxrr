# Security and Data-Integrity Review: PCD Export/Import Atomicity

## Executive Summary

Code review only; no exploit execution or implementation changes. Paths below are relative to repository root. Main evidence lies under `packages/praxrr-app/src/lib/server/` unless stated otherwise.

YAN-463 remains a confirmed persistence defect: export publishes SQL audit artifacts, but import reads only entity files. The next orphan sweep disables exported SQL while original drafts remain superseded. Excluding exports from the sweep preserves one installation but does not make fresh clones reproduce exported state.

Current worktree already contains a broader YAN-466 rollback snapshot in `pcd/ops/importBaseOps.ts:401-435`, not merely state restoration described in task input. This improves ordinary exception recovery but is not atomic: process termination, rollback errors, compile side effects, and concurrent writes remain outside its guarantee. Prefer native app-DB transactions plus explicit cache publication ordering and repository-operation serialization.

Additional findings: unrestricted export file paths, destructive cleanup races, credential-bearing Git URLs, mutable repository reads, and unbounded parsing. CRITICAL here means serious durable data loss or host-file integrity risk, not proven unauthenticated remote exploitation.

## Authentication and Authorization

Global `hooks.server.ts:229-293` supplies auth middleware and CSRF guard. Auth can be bypassed intentionally through `AUTH=off` or local-network mode. Changes actions do not perform per-user ownership checks in inspected code; design appears instance-wide rather than tenant-scoped. `canWriteToBase` and writer require configured PAT plus disabled local overrides for ordinary base edits; repo import context intentionally bypasses that requirement. PAT presence is capability configuration, not user authorization or proof of remote write permission.

Preserve global auth/CSRF. Enforce path and selection validation inside exporter even if routes already validate. `resolveSelectedOps` checks database ID, base origin, and draft state, a useful defense against cross-database op selection. Do not expose internal repo-import bypass through public request fields. Confirm deployment policy before adding tenant permissions not requested by feature.

## Data Protection

App DB and Git are separate durability domains; no SQLite transaction can make remote push atomic. Maintain clear outcomes and idempotent reconciliation keyed by committed tree/commit. Retain last-good published base on import failure and preserve drafts until verified canonical publication. Snapshots are recovery aids, not substitutes for atomic writes; manager's pre-pull snapshot is explicitly best-effort and remote-source-only in inspected flow.

Compile is not pure validation: it mutates op state/history and may resolve conflicts. Transaction scope must account for those writes. Cache publication is an independent in-memory side effect; invalidating after rollback avoids stale service but does not restore already-closed last-good cache. New implementation should make candidate build/publication ordering explicit.

Export must preserve exact config-name identifiers, explicit `arr_type`, stable identity, dependencies, deletes, and renames. Persisted names must not be trimmed to solve path safety. Generate filenames separately through existing slug utilities and resolve collisions deterministically.

## Dependency Security

Reader uses installed `@std/yaml`, JSON parser, existing portable validators/deserializers, SQLite, and system Git. No new dependency needed for atomicity or path confinement. No vulnerability scan performed; no dependency-CVE claim made.

`syncDependencies` runs between pull and import and can change schema content outside app-DB rollback. Include resolved schema ref/content in immutable import plan and recovery analysis. Validate schema/operator compatibility before publication. Git is invoked through argument arrays, avoiding shell interpolation; argument arrays do not eliminate Git option/pathspec interpretation or inherited Git configuration risks.

## Input Validation

Reject malformed repository payloads before writes; existing reader aggregates issues and importer fails before mutation. Duplicate stable identities currently compared using exact string values, while entity presence uses case-insensitive names; test case-variant identity duplicates and rely on deterministic upfront validation, not a late unique-constraint failure.

Add explicit bounds for request op IDs, file count, path lengths, commit-message size, entity file sizes, directory recursion, and YAML parsing workload. Confirm all form entries are strings instead of relying on TypeScript casts. Preview does not bind export to preview content: revalidate state/hash at commit and reject changed selection/source rather than silently publishing different data.

For entity YAML writes, use allowlisted directory mapping plus slug helper; check rename collisions and prune only selected prior canonical paths. Refuse symlinks and unknown path patterns. Include deletion tests, because copying files alone cannot publish deletions safely.

## Infrastructure Security

`execGit` disables terminal prompts and credential helpers but retains inherited environment/configuration. Restrict repository origins and file-system access appropriate to deployment. Avoid blanket Deno filesystem permission changes as an atomicity fix. Keep credentials out of persistent Git remotes; ensure temporary credential cleanup failures are visible without printing secrets.

Require non-force push and branch/HEAD checks. Remote advancing after preflight should fail safely through normal push rejection; this does not protect mutable local state during export. Repository/schema content should be imported from immutable commit identity, with repository operations serialized.

## Secure Coding Guidelines

1. Parse and validate repository sources before opening app-DB transaction; avoid Git/network work while transaction is open.
2. Serialize per-repository mutations and singleton DB transaction ownership across awaits; do not restore a stale snapshot over another successful operation.
3. Include orphan sweep, rewritten rows, inserted rows, op history, and destructive compile side effects in defined atomic boundary.
4. Publish candidate cache only after commit. On failure, close candidate; retain last-good cache where possible.
5. Produce canonical entity files from validated selected state, not all registered-cache contents, which may include unselected drafts/user overrides.
6. Preserve input validation, exact names, explicit Arr mapping, dependency groups, and deterministic filenames.
7. Fail safely on invalid files or paths; return bounded sanitized errors, keep raw credentials out of logs.
8. Verification: inject failure after first rewrite, first insert, sweep, cache build, auto-override, push, and bookkeeping; assert full rows/history/cache equivalence or explicit reconciliable published outcome. Test crash/restart, concurrent sync/export, traversal/symlink rejection, and fresh-clone import equivalence.

## Open Questions

- Are concurrent PCD service calls serialized outside inspected manager/exporter methods, including route exports and branch switches?
- Should compile/auto-override failures roll back accepted canonical import, or become separate post-import outcomes? Define before transaction scope.
- Does repository URL validation elsewhere reject hostname-prefix lookalikes, embedded credentials, local paths, and unsupported protocols?
- Is absent `entities/` intentional deletion of all canonical entities, unsupported legacy repository, or error?
- Which existing serializer can project selected base changes without user layer or unselected drafts? How are deletions and renames encoded?
- Can schema dependency refresh be staged and restored alongside failed import, especially when next sync sees no newer Git commit?
- Which exact app-DB tables can each deserializer/compile/override mutate, and do any use nested transactions?
- What reconciliation contract applies when remote push succeeded but local pull/import/bookkeeping failed?
- Does deployment permit untrusted local users to inspect Git process arguments or export temporary directories?
