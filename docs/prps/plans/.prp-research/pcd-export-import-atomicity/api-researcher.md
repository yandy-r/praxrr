| History before ops: cascade                | [SQLite FK actions](https://sqlite.org/foreignkeys.html#fk_actions) — updated 2026-03-20; repo `042_create_pcd_op_history.ts`                                                                                                                      | `pcd_op_history.op_id` references `pcd_ops.id ON DELETE CASCADE`. | Ops self-FK: deletion-order trap           | [SQLite immediate FK constraints](https://sqlite.org/foreignkeys.html#fk_deferred) — updated 2026-03-20; repo `041_create_pcd_ops.ts`                                                                                                              | `superseded_by_op_id` references `pcd_ops(id)` with default NO ACTION and immediate checking. If pre-existing op now references newly inserted op, deleting new ops **before** restoring existing rows fails `FOREIGN KEY constraint failed`. Within sync transaction, first clear only references to doomed IDs, then perform history-delete, op-delete, exact snapshot UPDATEs. Example: `UPDATE pcd_ops SET superseded_by_op_id = NULL WHERE database_id = ? AND superseded_by_op_id IN (SELECT id FROM pcd_ops WHERE database_id = ? AND id > ?);` Transient NULLs disappear when every snapshot column is restored. **Confidence: High** — schema and documented statement-end FK checks. |
| Deferred-FK alternative                    | [SQLite `defer_foreign_keys`](https://sqlite.org/pragma.html#pragma_defer_foreign_keys), [FK deferred constraints](https://sqlite.org/foreignkeys.html#fk_deferred) — FK docs updated 2026-03-20                                                   | `PRAGMA defer_foreign_keys = ON` defers all FK checks until outer COMMIT; allows temporary dangling self-FKs during delete-before-restore. Explicit self-FK cleanup is narrower. `PRAGMA foreign_keys = OFF` inside transaction is a no-op, not solution. **Confidence: High** — primary pragma/FK docs.                                                                                                                                                                                                            |
| Exact restoration: UPDATE, not REPLACE     | [SQLite REPLACE semantics](https://sqlite.org/lang_conflict.html#replace) — live docs accessed 2026-10-07; [FK cascade](https://sqlite.org/foreignkeys.html#fk_actions) — updated 2026-03-20                                                       | `INSERT OR REPLACE` deletes conflicting existing row before insert; can cascade-delete pre-import history. Restore existing snapshot rows via parameterized UPDATE of **all stored columns**, explicitly binding original `created_at`/`updated_at`, NULLs and metadata text; avoid helpers that force CURRENT_TIMESTAMP. Unexpected missing original row must fail restoration or use explicit INSERT, never silently succeed. **Confidence: High** — primary REPLACE/cascade semantics.                                                                                                                                                                                                      |
| Watermarks do not identify operation owner | [SQLite isolation](https://sqlite.org/isolation.html), [SQLite AUTOINCREMENT](https://sqlite.org/autoinc.html) — live docs accessed 2026-10-07                                                                                                     | IDs greater than pre-import watermark identify later inserts, not import-owned inserts. `database_id` scoping protects other databases, but concurrent same-database user writes could still be deleted/restored. Compensation transaction is atomic only for restoration; it does not make async import crash-atomic or undo modified pre-watermark history. Do not reset sqlite_sequence solely to reuse failed-import IDs. **Confidence: High** for SQLite behavior; ownership risk follows from proposed predicates.                                                                         |
